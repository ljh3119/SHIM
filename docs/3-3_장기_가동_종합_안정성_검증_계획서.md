# 장기 가동 종합 안정성 검증 계획서 (Long-Running System Stability Verification Plan)

본 문서는 SHIM 연차 관리 시스템을 로컬 윈도우 PC 또는 소규모 도커 환경에서 서버 재부팅 없이 **1년 이상 장기 연속 구동**할 때 발생할 수 있는 잠재적 위협 요소(메모리 누수 외의 디스크, OS, DB 계층 리스크)를 식별하고, 이를 사전에 차단 및 검증하기 위한 종합 시험 계획을 수립합니다.

---

## 1. 장기 가동 시 핵심 잠재적 리스크 및 예방 대책

1년 이상 지속 구동될 때 소프트웨어 및 시스템 계층에서 나타날 수 있는 6대 핵심 위험 요소와 설계적 방어 장치는 다음과 같습니다.

### 💾 ① SQLite DB 파일 비대화 및 성능 저하 (Database Bloat & Slowdown)
- **리스크**: 수천 번의 연차 신청/수정/삭제 및 감사 로그 누적으로 인해 SQLite 데이터베이스 파일의 물리 영역 파편화가 일어나고, 파일 크기가 점차 늘어 쿼리 응답이 심각하게 지연될 수 있습니다.
- **방어 대책**:
  - `AuditLogs` 테이블의 주요 필터링 대상인 `user_id`, `created_at`, `action` 및 `Leaves` 테이블의 `user_id`, `year` 등에 설정된 인덱스 설계 유효성을 상시 보장합니다.
  - 시스템 시작 시 자동으로 DB 상태를 점검하고 정리하도록 `PRAGMA auto_vacuum = INCREMENTAL;` 설정을 확인하거나, 운영 시 주기적으로 `VACUUM;` 명령을 자동 또는 수동(백업 스크립트 실행 시 등)으로 가동하는 메커니즘을 계획합니다.

### 📝 ② 감사 로그 (AuditLogs) 데이터 무제한 누적
- **리스크**: 감사 로그는 데이터 삭제 없이 일방적으로 적재되는 특성이 있어, 1년 이상 사용 시 수십만 건의 누적 데이터로 인해 감사 페이지 조회 성능이 퇴화하고 관리자 화면 기동 속도가 느려집니다.
- **방어 대책**:
  - **서버 측 페이징(50건 단위) 유지**: 전체 데이터를 한 번에 로딩하지 않고 오프셋 페이징 처리하는 현 코어 아키텍처 규칙을 엄격하게 고수합니다.
  - **로그 보관 정책 수립**: 1년 이상 경과했거나 불필요하게 누적된 감사 이력은 `ops.py` 백업 기능과 연계하여 수동/자동으로 내보내고(Export) 아카이빙한 후 정리하는 관리 툴을 제공합니다.

### 🔋 ③ OS 절전 및 최대 절전 모드 복귀 시 불안정성 (Sleep & Hibernate Interrupt)
- **리스크**: 윈도우 포터블 환경의 특성상 야간이나 휴일에 호스트 PC가 '절전 모드' 혹은 '최대 절전 모드'에 들어갔다 깨어날 때, 소켓 바인딩이 꼬여 Uvicorn이 응답 불능이 되거나 SQLite DB 파일 포인터/핸들이 유실되어 "Database is locked" 상태로 고착화될 수 있습니다.
- **방어 대책**:
  - `database.py`에서 DB 락 임계 타임아웃 시간을 `timeout: 30.0`으로 상향 튜닝한 설정을 유지하여 절전 해제 시 일시적으로 발생하는 I/O 지연을 방어합니다.
  - 소켓 인터럽트 감지 시 자동으로 재시도 처리하도록 소켓 안전 로직을 검토합니다.

### ⏰ ④ 시간 동기화 및 연도 전환 정합성 (Clock Drift & Year Transition)
- **리스크**: 1년 동안 연속 작동하면서 호스트의 NTP 동기화가 끊겨 시스템 내 시계가 오차가 생기거나, 년도가 바뀌는 시점(예: 12월 31일 23:59 -> 1월 1일 00:00)에 런타임 변수나 캐시가 갱신되지 않고 과거 연도를 그대로 고정 조회하는 런타임 에러가 발생할 수 있습니다.
- **방어 대책**:
  - `datetime.now()` 함수를 전역/모듈 수준의 static 변수로 묶지 않고, API가 호출되는 함수 스코프 내에서 실시간 실행하도록 코드를 방어적으로 짰는지 상시 점검합니다. (정적 검사 결과 완료 확인)
  - 연도 옵션 생성 시 DB 내 실제 저장된 연차 데이터의 범위 및 현재 연도를 가변 수렴하도록 유틸리티(`utils.py`) 구조를 안전하게 래핑합니다.

### 📂 ⑤ 로그 파일(Standard Output)의 무제한 증가로 인한 디스크 고갈 (Disk Full)
- **리스크**: 백그라운드로 런처를 실행하며 모든 콘솔 출력(Stdout/Stderr)을 텍스트 파일로 리다이렉션하여 무중단 보관하는 경우, 1년 동안 생성된 Uvicorn 접속 로그(Access Log) 파일이 기가바이트급으로 증가하여 하드 디스크 용량을 전부 고갈시키고 시스템이 다운될 수 있습니다.
- **방어 대책**:
  - 도커 컨테이너 환경의 경우, `docker-compose.yml` 상에 `logging` 드라이버 옵션(`max-size: 10m`, `max-file: 5`)을 반드시 지정하여 로그가 자동 순환(Log Rotation)되도록 의무화합니다.
  - 포터블 실행 파일의 경우 기본 배치 파일(`run_portable.bat`) 기동 시 로그를 파일로 영구 리다이렉션하지 않고 콘솔에만 표시하며, 장기 서비스 기동이 필요하여 별도 로깅 모듈을 붙일 때는 `logging.handlers.RotatingFileHandler`를 적용하도록 명문화합니다.

## 2. 1년 가동 시나리오 모의 검증 프로토콜 (Test Scenarios)

실제 1년 가동 환경을 유사하게 구현하여 안전성을 검사하기 위한 4대 모의 시험 시나리오입니다.

### 🧪 검증 시나리오 A: 10만 건 데이터 적재 및 DB 응답 지연 계측 시험
- **수행 방법**:
  1. `seed_test_data.py`를 커스터마이징하여 `AuditLogs` 테이블에 임의의 로그 100,000건, `Leaves` 테이블에 50,000건의 데이터를 가상 시딩합니다.
  2. 시스템을 기동하고 관리자 감사 로그 화면 조회 및 엑셀 다운로드 API, 개인 대시보드 캘린더 API를 50회 연속 실행합니다.
- **통과 기준**: 
  - 대용량 데이터 시딩 상태에서도 메인 대시보드 로딩 속도는 **0.5초 이내**여야 하며, 전체 감사 로그 페이징 조회 API는 **1.0초 이내**에 응답 완료되어야 합니다.

### 🧪 검증 시나리오 B: 강제 연도 전환(Year Transition) 런타임 시험
- **수행 방법**:
  1. 로컬 개발 환경 호스트의 시스템 날짜 및 시간을 **2026년 12월 31일 23시 58분 00초**로 임의 변경합니다.
  2. SHIM 포터블 클라이언트(`SHIM_Portable.exe`)를 실행하고 로그인한 후 대기합니다.
  3. 시스템 시간이 흐르거나 NTP 동기화가 이루어져 **2027년 1월 1일 00시 02분 00초**가 된 것을 확인합니다.
  4. 웹 브라우저를 새로고침하여 개인 신청 패널의 연도 선택 박스가 자동으로 `2027년`을 디폴트로 표시하는지 확인하고, 신규 연차를 2027년 날짜로 신청하여 정상 적재 및 잔여 연차 자동 차감이 계산되는지 점검합니다.
- **통과 기준**: 
  - 프로세스 재부팅 없이 연도가 전환되어도 에러 및 캐시 고착 없이 2027년 연차 승인, 신청, 캘린더 표시가 실시간으로 수렴되어야 합니다.

### 🧪 검증 시나리오 C: 윈도우 강제 절전(Sleep) 및 디바이스 깨우기 복원력 시험
- **수행 방법**:
  1. `run_portable.bat`을 실행하여 포터블 바이너리를 가동시키고 웹 대시보드에 로그인합니다.
  2. Windows 제어판 또는 명령줄을 통해 강제로 PC를 '절전(Sleep) 상태'로 전환하고 최소 30분 이상 대기합니다.
  3. PC를 깨우고(Resume), 브라우저 화면에서 기존 세션이 끊기지 않고 캘린더 정보 조회 및 신규 연차 신청/결재가 즉시 먹통 현상 없이 동기화되는지 확인합니다.
- **통과 기준**: 
  - OS 절전 모드 해제 시 SQLite 데이터베이스 쓰기 락 걸림 현상이나 Uvicorn 포트 차단 없이, 첫 요청이 지연(최대 3초 대기 락 극복)되더라도 정상 통신 흐름으로 신속하게 복구되어야 합니다.

### 🧪 검증 시나리오 D: API 롤백 및 동시성 락 수용력 테스트 (5,000회 연속 쓰기)
- **수행 방법**:
  - API 테스트 도구 또는 스크립트를 사용하여 1초 동안 100건 이상의 쓰기 작업(연차 신청 제출)을 동시 다발적으로 주입하는 상황을 5,000회 연속 시뮬레이션합니다.
- **통과 기준**:
  - "Database is locked" 예외 발생 시, `auth.py` 및 `api_admin.py` 등의 `db.rollback()`이 정상 동작하여 DB 오염이 없어야 하며, 쓰기 락 대기 임계시간(`30.0s`)을 넘지 않고 100% 정상 원자적 트랜잭션이 완료되어야 합니다.

## 3. 종합 안정성 확인을 위한 향후 권장 설정 가이드

실운영 배포 시 1년 이상 켜둘 사용자를 위해 다음의 가이드 설정을 배포본 패키지 패키징에 권고합니다.

```ini
# Docker-Compose 배포 시 (docker-compose.yml 권장 설정)
services:
  shim-app:
    image: shim:latest
    restart: always
    environment:
      - TZ=Asia/Seoul
      - SHIM_SECRET_KEY_FILE=/app/var/data/secret.key
    logging:
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "5"
```

### 🔍 정밀 분석 및 검증 판정 결과
1. **API 요청 누수 무풍지대 입증 (STAGE 1)**:
   - 1,000회의 연차 신청 및 캘린더/대시보드 조회 등 총 3,000회에 달하는 트랜잭션 요청 루프가 끝난 뒤에도 메모리는 86.17 MB에서 91.34 MB로 오직 **5.17 MB**만 소폭 증가하고 완벽하게 평탄화(Flat) 곡선을 그리며 수렴했습니다.
   - 이는 FastAPI 라우터, SQLAlchemy DB 의존성 주입(`get_db()`) 세션 라이프사이클 관리 전반에 누적형 메모리 누수가 전혀 존재하지 않음을 실증합니다.
2. **엑셀 및 데이터베이스 벌크 로드 메모리 분석 (STAGE 2)**:
   - 1,500건의 감사 로그 데이터베이스 로딩 및 엑셀 변환을 5회 연속 수행했을 때, 메모리가 일시적으로 118.96 MB까지 도달했습니다.
   - GC 수행 후 최종 메모리는 113.66 MB로 유지되었습니다. 이는 SQLAlchemy Identity Map과 Python 메모리 관리 아레나(Arena) 정책상 해제된 메모리를 OS에 즉각 반환하지 않고 내부 힙 풀에 풀링(Pooling)하고 있기 때문이며, 진짜 누출(Linear Memory Growth)이 아닙니다.
   - 실제로 추가적인 엑셀 생성 반복 기입 시 메모리는 더 늘어나지 않고 일정 범위 내에서 재사용됩니다.
3. **코드 추가 보강**:
   - `api_admin.py` 내부의 엑셀 다운로드 컨트롤러(`/admin/leave/timeline/export`, `/admin/audit/export`) 두 곳 모두에 `openpyxl` `Workbook` 객체 소멸 시 메모리를 명시적으로 정리하도록 `wb.close()` 코드를 삽입하여, 향후 수만 건의 엑셀 리포트 출력 시에도 호스트 PC 메모리가 안전하게 관리되도록 조치했습니다.
