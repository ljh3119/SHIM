# 향후 개선계획 (Product Roadmap)

이 문서는 아직 완료되지 않은 백로그만 관리합니다. 완료된 변경과 검증 증적은 `docs/2-1_운영_릴리즈_통합_산출물.md`, 구현 후의 현재 구조는 `docs/4-1_SHIM_프로젝트_설계서.md`에서 관리합니다.

SHIM은 폐쇄망에서 로컬 Windows, Docker, 포터블 실행을 지원하는 단일 FastAPI·SQLite 애플리케이션입니다. 새 서버·서비스·런타임 의존성은 실제 운영 요구가 확인된 경우에만 추가하고, 기존 코드와 Python 표준 라이브러리로 해결 가능한 범위를 우선합니다.

- **기준 버전**: `1.12.3` 소스
- **UI 감사 후속 과제**: 2026-11-15 Hallmark 감사와 설명 화면 검토를 바탕으로 `UI-A11Y-001`, `UI-DOM-001`, `UI-A11Y-002`, `UI-A11Y-003`을 미완료 과제로 등록했습니다. 이번 변경은 문서 기록이며 제품 구현·버전 변경·재패키징·운영 배포를 포함하지 않습니다.
- **기준 상태**: v1.11.0 C BASELINE 통합(PR #5, 커밋 `34c6b4f`) 및 v1.12.0 Hallmark UI polish 검증(smoke 17개, 화면 90개, 모달 20개, 기간 저장 2건, native 200% 등) 완료 상태를 기준으로 합니다.

- `DEP-001`은 `cryptography 50.0.0` 코드·감사·산출물 검증을 완료했으나, GitHub 게시 후 Dependabot 경고 종료 확인이 남아 있으므로 아래 게시 확인 대기 과제로 유지합니다.
- 조건부 개선 과제인 DB 스키마 마이그레이션 안전성 보강(`DB-001`), 오프라인 암호화 키 로테이션(`SEC-004`), 로그인 남용 제한(`AUTH-002`), 그리고 최소 CI(`CI-001`)는 미완료 상태를 그대로 유지하며 완료로 표시하지 않습니다.
- 포터블 실제 종료와 안내 일치(`OPS-005`)는 후속 과제로 등록했습니다. 이번에는 기록만 추가하며 구현·버전 변경·재패키징은 진행하지 않습니다.
- Hallmark 의심 항목인 Gate 73 대시보드 활동 로그 겹침과 Gate 56 팀 달력 스크롤 교차는 2026-11-14 사용자 직접 확인에서 문제가 보고되지 않아 추가 수정 없이 검토를 종결했습니다. 사용자 확인 범위의 미재현 결과이며, 자동 검사 원본은 보존하고 같은 증상이 재현되면 다시 검토합니다. 확인 경위는 `docs/2-1_운영_릴리즈_통합_산출물.md`에 기록합니다.
- 자동복구는 현재 애플리케이션이 요구하는 스키마 완료 상태와 호환되는 백업만 허용하며, 구버전 DB 마이그레이션은 자동복구와 결합하지 않습니다.
- 수정 버전이 없는 `ecdsa 0.19.2 / PYSEC-2026-1325`는 SHIM이 HS256만 허용하고 ECDSA·ECDH 경로를 사용하지 않는다는 근거로 해당 ID만 제한적으로 수용합니다.
- **의존성 경고 확인(2026-11-14)**: GitHub 경고 20·21은 `python-jose 3.5.0`의 동일 취약점 [CVE-2026-85394](https://github.com/advisories/GHSA-3qf3-8w2g-rqmx)가 운영·개발 manifest에 각각 표시된 것입니다. 현재 SHIM의 고정 HS256·대칭 비밀키 경로와 공격 조건을 대조했으며 경고를 해제하거나 라이브러리 결함이 해결됐다고 처리하지 않았습니다. 상세 근거는 배포본의 `SECURITY_NOTE.md`에 보관합니다.
- 저장소가 직접 관리하는 GitHub Actions 워크플로와 `main` 브랜치 보호는 아직 없습니다. 사용자 결정에 따라 `CI-001`은 다른 남은 과제를 검토한 뒤 가장 마지막에 처리합니다.
- 본 기준일자 및 버전 갱신은 백로그 임계치나 운영 정책의 신규 채택을 뜻하지 않습니다.

### 공통 원칙

- 기존 테스트·작업 로그·릴리스 증적에서 사용한 작업 ID를 다른 의미로 재사용하지 않습니다.
- 한 번에 하나의 작업 ID만 구현하고 표적 테스트를 먼저 추가합니다.
- 신규 테스트는 `tools/scripts/run_tests.py`의 smoke 또는 release 목록에 등록합니다.
- 운영 DB·키·설정 파일을 바꾸는 작업은 서비스 중지, 검증된 사전 백업, 실패 복구와 배포 형태별 리허설을 완료하기 전 운영 가능으로 판단하지 않습니다.
- 공개 HTTP 응답에는 경로, SQL, 예외 원문, 키, 암호문, 개인정보와 백업 세부 정보를 노출하지 않습니다.
- 구현이나 Docker·포터블 실환경 검증이 남으면 해당 과제를 완료 처리하지 않습니다.

## 2. 게시 확인 대기

### [DEP-001] cryptography 보안 업데이트 게시 확인

- **완료된 범위**: `cryptography 50.0.0` 고정, Windows 64비트 Python 3.12의 Fernet·HS256, 전체 smoke·release, `pip check`, `pip-audit==2.10.1`, Docker와 포터블 실기동 검증을 완료했습니다.
- **남은 작업**:
  - v1.9.8 변경을 커밋·태그·push한 뒤 `origin/main`의 `requirements.txt`와 배포 산출물이 `cryptography 50.0.0`을 사용하는지 확인합니다.
  - GitHub Dependabot에서 기존 `cryptography` 경고가 자동 종료됐는지 확인합니다. 자동 종료되지 않으면 경고가 참조하는 manifest와 브랜치, 실제 감사 결과를 대조하며 근거 없이 수동 종료하지 않습니다.
- **완료 기준**: 게시된 커밋·태그 식별값과 Dependabot 경고 종료 상태를 릴리스 통합 산출물에 기록한 뒤 이 항목을 삭제합니다.

## 3. 확인된 UI 개선 과제

아래 과제는 `1.12.3` 소스의 Hallmark 감사에서 확인한 문제입니다. 현재는 등록만 완료했으며 수정 구현은 하지 않았습니다. 사용자 설정, 연차 차감, 신청·결재 API와 DB 구조는 변경 범위에 포함하지 않습니다.

### 감사 근거와 해석 범위

- **기준 소스**: `main fe68954`. 작업 트리에 있던 관리자 달력 최소 폭 수정과 릴리스 문서 변경은 별도로 보존합니다.
- **실행 범위**: 고유 URL 11개, 역할별 화면 12개를 8개 CSS 뷰포트에서 총 96회 렌더링했습니다. 이는 기본 화면의 레이아웃 검사 횟수이며 모든 상태·모달을 96회씩 조작했다는 뜻은 아닙니다. 대표 상호작용은 별도로 확인했습니다.
- **감사 증적**: 작업 환경의 `artifacts/hallmark-full-audit-20261115-hydrogen/`에 정정 보고서와 후속 실측 결과를 보관합니다. `artifacts/ui-audit-explainer-20261115/`에는 비교 설명과 추가 브라우저 측정값을 보관합니다. 이 경로들은 로컬 증적이며 Git에 포함되거나 배포 패키지에 동봉된 자료로 간주하지 않습니다.
- **설명 예시**: 비교 HTML은 문제 이해를 위한 모형입니다. 오른쪽 개선 예시, 색상 대안과 중복 ID 동작 모형을 실제 제품 수정·배포 또는 모든 기기의 재현 결과로 인용하지 않습니다.

### [UI-A11Y-001] 기간 선택 토글의 접근성 이름·상태 제공

- **상태**: 미구현. 다음 사용자 화면 접근성 보완 작업에서 처리합니다.
- **대상·확인 근거**: [개인 달력](../src/templates/user_calendar.html)과 [팀 달력](../src/templates/user_team_calendar.html)의 `#multiSelectToggleBtn`에 접근성 이름과 ON/OFF 상태 속성이 없습니다. 옆의 ‘기간 선택’ 텍스트가 버튼의 접근성 이름으로 연결되지 않습니다. 키보드 포커스 링은 현재도 정상 표시되므로 새 결함으로 취급하지 않습니다.
- **사용자 영향**: 화면 낭독기를 사용하는 사용자는 버튼의 목적과 현재 켜짐·꺼짐 상태를 정확히 알기 어렵습니다. 일반 마우스 클릭이 실패한다는 의미는 아닙니다.
- **재현·확인 방법**:
  - 개인·팀 달력에서 키보드 Tab으로 토글에 접근하고 브라우저 접근성 트리의 이름·역할·현재 상태를 확인합니다.
  - 마우스, Enter, Space로 상태를 바꾼 뒤 실제 선택 모드와 접근성 상태를 대조합니다.
- **수정 범위**:
  - 버튼에 ‘기간 선택’ 이름을 연결하고 `role="switch"`와 `aria-checked`로 상태를 제공합니다. 기존 상태 변경 함수에서 실제 모드와 함께 갱신합니다.
  - 새 진입·새로고침 기본 OFF, 날짜 입력·복원에 의한 자동 ON 금지, 같은 문서의 화면 전환 시 사용자 모드 유지와 OFF 전환 시 날짜·사유 보존을 유지합니다.
- **완료 기준**:
  - 개인·팀 달력의 최초 OFF와 직접 ON/OFF가 접근성 트리 및 화면 낭독기에 일치하게 전달됩니다. 낭독 문구 자체는 제품·브라우저별로 다를 수 있습니다.
  - PC partial 지연 로딩과 390↔1440px 전환 후에도 실제 상태와 `aria-checked`가 일치하고 기존 포커스 링이 유지됩니다.
  - 기존 기간 전일 제한, 반차 선택과 실제 신청 동작에 회귀가 없습니다.

### [UI-DOM-001] 신청 이력과 관리자 모달의 중복 ID 제거

- **상태**: 미구현. 중복 ID 존재는 확인했으며 모든 기기에서 클릭 오동작이 재현된 것으로 기록하지 않습니다.
- **대상·확인 근거**:
  - [신청 이력 partial](../src/templates/partials/user_leave_timeline.html)의 `shim-timeline-accordion`, `timeline-accordion-arrow`, `timeline-accordion-content`가 PC용·모바일용 영역에 함께 마운트되면서 중복됩니다. `toggleTimelineAccordion()`은 `getElementById`로 문서에서 먼저 찾는 요소를 참조합니다.
  - [관리자 사원 화면](../src/templates/admin_users.html)의 등록·수정 모달 제목이 모두 `id="modal-title"`이며 두 창의 `aria-labelledby`도 같은 값을 참조합니다.
- **사용자 영향**: 눌렀던 이력과 다른 영역이 접힐 위험이 있고, 보조기기가 모달 제목을 잘못 연결할 수 있습니다. 중복 ID가 존재한다는 사실과 실제 오동작 재현 범위를 구분해 기록합니다.
- **재현·확인 방법**:
  - PC partial 로딩을 완료한 개인·팀 달력에서 문서 전체의 ID 중복을 수집합니다. PC·모바일 이력을 각각 접고 펼친 뒤 변경된 영역을 확인합니다.
  - 모바일 최초 진입 후 PC 폭으로 전환하고 다시 모바일로 돌아와 반복합니다. 사원 등록·수정 창을 각각 열어 실제 제목과 접근성 이름을 대조합니다.
- **수정 범위**:
  - 이력 partial에 마운트 영역별 식별자를 전달해 세 ID를 구분하고, 클릭한 아코디언을 기준으로 내용과 화살표를 찾도록 관련 호출부를 함께 수정합니다.
  - 모달 제목 ID를 `add-user-modal-title`, `edit-user-modal-title`로 구분하고 각 `aria-labelledby`를 연결합니다.
  - 이력 기본 펼침·접힘, 상대 시간, 상태·반려 사유 표시와 모달 폼 동작은 유지합니다.
- **완료 기준**:
  - 최초 로드·partial 로드·390↔1440px 전환 후 대상 ID가 중복되지 않습니다.
  - 각 이력 버튼이 자기 영역의 내용·화살표만 변경하며 숨겨진 반대 화면의 요소를 잘못 조작하지 않습니다.
  - 등록·수정 모달이 각각 올바른 제목으로 식별되고 ESC 닫기·포커스 복귀·기존 저장 동작에 회귀가 없습니다.

### [UI-A11Y-002] 팀 달력 공휴일 글자 대비 개선

- **상태**: 미구현. 일반 텍스트 대비 기준에 조금 못 미치는 것으로 확인했습니다.
- **대상·확인 근거**: [팀 달력](../src/templates/user_team_calendar.html)의 `.holiday-head` 글자 `#d92d20`, 배경 `#fef3f2` 조합은 대비 원값이 약 `4.4441:1`입니다. 날짜·요일은 약 10~11px이므로 일반 텍스트 기준인 `4.5:1`과 비교합니다. 반올림해서 통과 처리하지 않습니다.
- **사용자 영향**: 시력이 낮거나 화면을 밝게 보는 환경에서 작은 날짜·요일을 구별하기 어려울 수 있습니다. 색이 ‘AI 전용’이거나 달력 기능이 실패한다는 의미는 아닙니다.
- **재현·확인 방법**: 공휴일이 있는 달을 열고 헤더의 실제 계산 글자색과 최종 합성 배경색을 구합니다. 투명도가 있다면 조상 배경까지 합성한 뒤 대비를 계산합니다.
- **수정 범위**:
  - 기존 빨간색 계열과 공휴일 의미를 유지하면서 기준을 충족하는 기존 의미색 토큰을 우선 사용합니다. 전역 팔레트 변경은 하지 않습니다.
  - 비교 HTML의 `#b42318`은 약 `6.05:1`인 설명용 대안이며 확정 제품 색상으로 채택한 것은 아닙니다.
- **완료 기준**:
  - 실제 렌더링 색상의 대비가 반올림 전 `4.5:1` 이상이고 날짜·요일 글자가 겹치거나 잘리지 않습니다.
  - 주말·공휴일·선택 상태의 의미, 범례, 툴팁과 신청 동작이 유지됩니다. 28·29·30·31일 달 및 390·1023·1024·1440px에서 확인합니다.

### [UI-A11Y-003] 관리자 차트의 접근성 이름 연결

- **상태**: 미구현. 차트 외형 변경 없이 설명 연결을 보완하는 과제입니다.
- **대상·확인 근거**: [관리자 대시보드](../src/templates/admin_dashboard.html)의 `#teamChart`, `#trendChart` canvas에 접근성 이름이 없습니다. 화면에 제목이 보여도 차트 자체의 접근성 이름으로 자동 연결되는 것은 아닙니다.
- **사용자 영향**: 화면 낭독기로 그림을 탐색할 때 어떤 내용을 나타낸 차트인지 식별하기 어렵습니다. 일반 화면의 차트·툴팁이 작동하지 않는다는 의미는 아닙니다.
- **재현·확인 방법**: 관리자 대시보드의 두 canvas를 브라우저 접근성 트리에서 각각 선택하고 이름·역할과 연결된 설명을 확인합니다.
- **수정 범위**:
  - 두 차트에 `role="img"`를 제공하고 실제 제목을 `aria-labelledby`로 각각 연결합니다. 제목의 ID는 문서 내에서 유일해야 합니다.
  - 차트 명칭만으로 상세 수치를 전달할 수 없다는 한계를 남깁니다. 같은 데이터를 제공하는 기존 표가 있는지 확인하고, 없다면 텍스트 요약이나 데이터 표의 필요성을 검토 결과로 기록합니다. 이름만 추가하고 수치 접근성 전체가 해결됐다고 표시하지 않습니다.
  - 기존 집계·필터, 색상 토큰의 Canvas 변환, 툴팁과 동적 갱신 로직을 유지합니다.
- **완료 기준**:
  - 두 차트가 각각 ‘팀별 연차 사용 현황’, ‘월별 연차 사용 트렌드’에 대응하는 올바른 이름과 이미지 역할로 식별됩니다.
  - 차트 렌더링·툴팁·데이터 갱신과 콘솔 오류 여부를 확인하고 상세 수치 대체 설명의 제공 여부 또는 남은 범위를 함께 기록합니다.

### 오탐 정정과 별도 확인 대상

- **모션 감소 미대응 지적 철회**: [CSS 소스](../src/static/css/app.css)와 [생성 CSS](../src/static/css/tailwind.css)에 `prefers-reduced-motion: reduce` 시 지속 시간을 `0.01ms !important`로 줄이는 규칙이 이미 있습니다. 같은 생성 CSS와 `.fade-in` 규칙을 브라우저에서 확인한 결과 기본 `0.2s`, 감소 설정 `1e-05s`가 적용됩니다. `animationName`이 `fadeIn`으로 남는다는 이유만으로 미대응 결함으로 판단하지 않습니다. 신규 미완료 과제로 등록하지 않습니다.
- **PM 배지 대비 지적 철회**: 반투명 배경을 조상 배경과 합성하지 않은 계산 오류였습니다. 합성 후 약 `6.01:1`로 확인했으므로 기존 `1.66:1` 지적을 과제화하지 않습니다.
- **토글 포커스 링 누락 지적 철회**: 전역 `:focus-visible` 규칙에 따라 실제 Tab 접근 시 `2px solid`, offset `1px`가 표시됩니다. `focus:outline-none` 문자열만으로 결함을 단정하지 않습니다. 이름·상태 누락은 `UI-A11Y-001`로 별도 처리합니다.
- **기존 검토 종결 유지**: Gate 56 팀 달력 스크롤 교차와 Gate 73 대시보드 활동 로그 겹침은 기존 사용자 미재현 결론을 유지합니다. 이번 후속 측정에서도 겹침은 확인되지 않았으며 다시 재현되기 전까지 신규 확정 결함으로 등록하지 않습니다.
- **미검증 항목**: 팀 달력 비공개 설정의 차단 화면, 결재 반려 사유 프롬프트, 공휴일 등록 후 DOM 갱신, 사원 비밀번호 초기화·활성 전환 API, 다중 신청 버튼 활성 후 포커스는 후속 표적 확인 대상입니다. 감사 도구의 `false`나 미실행 값을 실제 제품 실패로 해석하지 않습니다.
- **환경 한계**: `sloplint --render`는 `puppeteer-core` 부재로 미실행이며 Playwright 실측이 모든 렌더 게이트를 대체하지는 않습니다. 실제 브라우저 200% 확대, Windows 브라우저와 Docker 컨테이너 실기동도 이번 감사의 검증 범위에 포함하지 않습니다. DPR 2 검사를 200% 확대 검사로 표기하지 않습니다.

## 4. 조건부 개선 과제

현재 즉시 착수할 필수 과제는 없습니다. 아래 과제는 적힌 조건이 실제로 확인될 때만 착수합니다.

### [DB-001] SQLite 스키마 마이그레이션 안전성 보강

- **현재 판단**: 저장소의 로컬 DB에는 데이터가 있지만 운영 데이터인지 개발 데이터인지 확인할 수 없습니다. “실제 사용자가 없다”는 전제를 코드나 문서에서 확정하지 않습니다.
- **착수 조건**:
  - 보존해야 할 배포 DB가 확인되거나,
  - 배포된 DB의 컬럼·인덱스·외래키를 변경하는 다음 요구가 생길 때 실제 스키마 변경보다 먼저 착수합니다.
- **필요 시 구현 범위**:
  - 배포 담당자가 지원 기준 DB 버전과 보존 대상 설치본을 먼저 명시합니다.
  - 기존 `schema_versions`, 초기화 잠금, SQLite backup API와 `quick_check`를 재사용합니다.
  - `Base.metadata.create_all()`이나 버전별 마이그레이션보다 앞서 일반 순환 백업과 분리된 `pre_migration` 백업을 만들고, 검증 성공 시에만 초기화를 계속합니다.
  - 실제 변경에 필요한 버전별·멱등 마이그레이션과 지원 대상 DB 복제본 테스트만 추가합니다.
- **제외 범위**:
  - 배포 여부 확인 없이 모든 과거 개발 DB를 소급 지원하지 않습니다.
  - 구체적인 스키마 변경 전에 범용 마이그레이션 프레임워크를 만들지 않습니다.
  - 현재 자동복구에 구버전 DB 마이그레이션을 결합하지 않습니다.
- **완료 기준**:
  - 지원 대상 DB 복제본에서 성공·실패·재실행·중단 복구, 행 수, `quick_check`, 외래키, 인덱스와 `schema_versions` 정합성을 검증합니다.
  - 실패 시 검증된 `pre_migration` 백업으로 운영자가 복구할 수 있고 원본과 실패 증적이 보존되는지 확인합니다.

### [SEC-004] 오프라인 암호화 키 로테이션

- **착수 조건**:
  - 암호화 모드의 실제 운영 배포에서 키 유출 대응, 정기 교체 정책 또는 고객 보안 요구가 확인되고,
  - 포터블·Docker 운영 복제본으로 중단·복구 리허설을 수행할 수 있을 때 착수합니다.
- **단계별 범위**:
  1. 읽기 전용 `verify`·`verify-backup`으로 DB 무결성, 지원 스키마, 현재 키 지문과 대상 암호문을 변경 없이 검사합니다.
  2. 서버를 완전히 중지한 상태에서 롤백 백업과 작업용 DB를 만들고 작업용 DB만 새 키로 재암호화합니다.
  3. 새 키 전체 복호화, 이전 키 복호화 실패, 행 수, `quick_check`, 외래키와 `key_hash_snapshot`을 검증한 뒤 DB와 키 설정을 각각 원자적으로 교체합니다. 두 대상을 하나의 원자 연산으로 오인하지 않습니다.
  4. 전체 `token_version`을 증가시키고 새 키 호환 백업을 생성·검증한 뒤 재기동합니다.
  5. DB와 설정 교체 사이의 강제 종료를 포함해 명시적 재개·롤백을 리허설합니다.
- **필수 안전 원칙**:
  - 키 원문을 명령행, 로그와 보고서에 출력하지 않습니다.
  - 평문 설치본은 `rotate-key`로 변환하지 않고 별도 요구의 `enable-encryption` 과제로 다룹니다.
  - 운영 DB를 행 단위로 직접 부분 변경하지 않고 작업 복제본을 검증한 뒤 교체합니다.
  - 포터블 키 파일과 Docker 외부 환경변수의 교체 절차를 분리하고, 작은 상태 파일로 중간 종료 시 재개 또는 이전 DB·키 세트 롤백을 지원합니다.
  - 이전 키 DB·키·설정 세트는 과거 백업의 보존 기간과 복구 리허설 완료 전까지 보존합니다.
  - 별도 GUI, 별도 유지보수 이미지와 무중단 다중 키 키링은 만들지 않습니다.
- **완료 기준**:
  - 잘못된 이전 키, 손상 암호문, 디스크 부족, WAL·SHM, 파일 교체 단계 중단, 재개·롤백과 권한 보존을 검증합니다.
  - 포터블과 Docker에서 중지→검증→로테이션→재기동→이전 키 백업 검증→롤백을 실제 리허설합니다.
  - 구현되지 않은 `rotate-key`, `verify-backup`, `enable-encryption` 명령을 현재 사용 가능한 절차처럼 문서화하지 않습니다.

### [AUTH-002] 로그인 남용 제한

- **착수 조건**: 반복 로그인 실패 기록, 신뢰할 수 없는 내부 접근 또는 고객 보안 감사 요구가 확인될 때 착수합니다.
- **구현 전 결정 사항**:
  - 직접 접속인지 역방향 프록시 뒤인지 확인하고 신뢰 가능한 클라이언트 IP 판정 방식을 먼저 확정합니다.
  - 재시작 시 제한 상태 초기화를 허용할지, 단일 프로세스 유지 여부와 허용 실패율·해제 시간을 운영 정책으로 정합니다.
- **기본 방향**:
  - 장시간 계정 잠금보다 짧은 지연 또는 IP·계정 조합별 제한을 우선합니다.
  - 단일 프로세스에서는 표준 라이브러리 기반의 작고 동시성 안전한 메모리 제한기를 우선하고 `slowapi`를 기본 전제로 두지 않습니다.
  - 관리자 특례, 영구 잠금과 DB 컬럼 추가는 명시적 고객 정책이 있을 때만 검토합니다.
- **완료 기준**:
  - 정상 로그인, 실패 누적·해제, 동시 요청, 프록시 환경, 재시작과 관리자 계정 서비스 거부 가능성을 검증합니다.
  - 제한 응답은 내부 계정 존재 여부를 추가로 노출하지 않고 정상 사용자를 과도하게 차단하지 않습니다.

### [OPS-005] 포터블 실제 종료와 안내 일치

- **상태·착수 시점**: 후속 과제로 등록하며, 다음 포터블 개선 작업에서 실제 Windows 검증 환경을 확보한 뒤 착수합니다. 현재는 구현하지 않습니다.
- **확인 사실**: 사용자가 확인한 폴더 삭제 불가는 테스트 시드 생성을 위해 열었던 CMD의 폴더 점유가 원인입니다. SHIM 서버 프로세스가 남은 것으로 확인된 사례는 아닙니다.
- **코드에서 확인한 개선점**: 트레이 종료 요청 전에 완료 알림을 표시하고, 최초 안내 런처는 서버 종료를 확인하지 않은 채 키 입력만 기다립니다.
- **개선 범위**:
  - 종료 요청 시에는 “종료 중”을 표시하고, 실제 서버 종료와 자원 정리를 확인한 뒤 완료 처리합니다. 실패·시간 초과를 성공으로 안내하지 않습니다.
  - 최초 안내 런처도 서버 종료를 감지해 입력 대기를 끝내고, 안내 문구를 실제 트레이 종료 절차와 맞춥니다.
  - 사용자가 별도로 연 CMD·PowerShell이나 다른 프로그램의 폴더 점유는 구분하며 해당 프로그램을 임의로 종료하지 않습니다.
- **완료 기준**:
  - 실제 Windows의 CMD ZIP·PyInstaller 패키지에서 정상 종료·종료 실패·시간 초과와 최초 안내 창을 열어 둔 상태·닫은 상태를 검증합니다.
  - 성공 시 해당 패키지의 런처·마스터·worker가 남지 않고, 종료 로그와 알림이 실제 결과에 일치하는지 확인합니다.
  - 외부 CMD가 없는 상태에서 폴더 삭제·이름 변경이 가능한지 확인하고, 시드용 CMD가 해당 폴더를 사용하는 경우와 구분합니다.

## 5. 최종 후순위 과제

### [CI-001] 최소 지속적 검증 및 의존성 감사

- **처리 순서**: 사용자 결정에 따라 남은 과제 중 가장 마지막에 검토·구현합니다. 앞의 조건부 과제가 아직 미착수여도 CI 착수 시점은 별도로 승인받습니다.
- **현재 판단**: 저장소가 직접 관리하는 Actions 워크플로와 브랜치 보호가 없고 로컬 pre-push 훅이 전체 smoke·의존성 감사를 실행하지 않습니다. Dependabot 보안 업데이트와 GitHub 관리형 Dependency Graph는 이미 활성화되어 있습니다.
- **최소 워크플로**:
  - Python 3.12에서 `requirements-dev.txt`를 설치합니다.
  - 검증된 고정 버전의 `pip-audit`를 별도 설치하고 Python 전체 컴파일, 버전 정합성, smoke와 `pip-audit -r requirements.txt`를 구분된 단계로 실행합니다.
  - Node 의존성 변경 시 `npm ci`와 `npm audit`을 실행합니다.
  - GitHub Actions 권한은 `contents: read`를 기본으로 하고 외부 Action과 감사 도구 버전을 검증된 값으로 고정합니다.
  - 실패를 `|| true`로 무시하지 않습니다. 이미 분석·수용한 `PYSEC-2026-1325`만 식별자, 영향 범위와 만료 조건을 기록해 제한적으로 예외 처리합니다.
- **저장소 설정**:
  - 워크플로가 안정화되고 실제 PR 기반 운영을 사용할 때 `main` 보호와 필수 상태 검사를 연결합니다.
  - secret scanning과 push protection은 저장소·계정에서 제공되는 범위를 확인한 뒤 활성화를 검토합니다.
- **제외 범위**:
  - 모든 push에 release·메모리 1,000회·Docker·포터블 빌드를 강제하지 않습니다. release 또는 배포 후보에서 별도로 수행합니다.
  - 기준선 없는 `mypy --strict`, 전면 lint 수정과 자동 배포를 추가하지 않습니다.
- **완료 기준**:
  - 정상 브랜치에서 필수 단계가 통과하고 의도적으로 실패시킨 테스트·버전 불일치·신규 미수용 감사 경고가 워크플로를 실패시킵니다.
  - 로컬 훅을 우회해도 원격 검사 결과가 남고, PR 보호를 사용한다면 실패 상태에서 병합이 차단됩니다.
  - 감사 결과 또는 승인된 예외를 릴리스 증적에 기록합니다.

## 6. 현재 채택하지 않는 범위

- 실제 고객 요구가 없는 OAuth, Redmine, 웹소켓, 외부 API와 프록시 구축
- `slowapi`, `structlog`처럼 현재 요구를 표준 라이브러리로 충족할 수 있는 신규 런타임 의존성
- 관리자 3회 실패·30분 잠금처럼 근거 없이 고정된 계정 잠금 정책
- 공개 `/health` 응답의 디스크·백업·내부 오류 세부 정보
- 중앙 로그 수집기 없는 환경의 전면 JSON 구조화 로깅
- 서비스 운영 중 수행하는 무중단 PII 키 로테이션과 다중 키 키링
- 실패를 `|| true`로 무시하는 감사·정적 분석 단계
- 기준선 없이 도입하는 `mypy --strict`, 전면 lint 수정과 자동 배포
- 구체적인 스키마 변경 전에 만드는 범용 마이그레이션 프레임워크

## 7. 구현 순서와 완료 처리

1. `DEP-001` — v1.9.8 게시 직후 Dependabot 종료 상태 확인
2. `UI-A11Y-001` → `UI-DOM-001` → `UI-A11Y-002` → `UI-A11Y-003` — 다음 UI 보완 작업에서 각각 독립 구현·검증. 현재는 과제 기록만 완료
3. `DB-001` — 실제 배포 DB 또는 다음 스키마 변경 요구가 확인될 때
4. `SEC-004` — 암호화 키 교체 요구와 배포별 리허설 환경이 확보될 때
5. `AUTH-002` — 접근 환경과 제한 정책이 확정될 때
6. `OPS-005` — 실제 Windows 검증 환경을 확보한 다음 포터블 개선 작업에서 처리
7. `CI-001` — 사용자 별도 승인 후 가장 마지막에 처리

조건부 과제는 앞 번호가 끝났다는 이유만으로 자동 착수하지 않습니다. 각 작업은 독립적으로 구현·검증하고, 일부 구현이나 실환경 검증이 남으면 완료 처리하지 않습니다.

완료 시 다음 원칙을 적용합니다.

1. 구현 후 현재 구조는 `docs/4-1_SHIM_프로젝트_설계서.md`와 관련 OpenWiki에 반영합니다.
2. 검사 결과와 산출물 식별값은 `docs/2-1_운영_릴리즈_통합_산출물.md`로 이관합니다.
3. 해당 작업 ID를 이 문서에서 삭제합니다.
4. 새 문서를 추가하지 않았다면 `docs/0_문서_인덱스.md`는 변경하지 않습니다.

## 8. 작업 인수인계 규칙

1. 작업 전에 `openwiki/quickstart.md`와 해당 영역 문서를 읽습니다.
2. `git status --short`와 대상 diff를 확인하고 사용자 미커밋 변경을 보존합니다.
3. 재현 테스트를 먼저 추가하고 smoke 또는 release 목록에 등록합니다.
4. 표적 테스트, smoke, 필요한 release와 Docker·포터블 실환경 검증을 순서대로 수행합니다.
5. 운영·보안·포터블 동작이 바뀌면 코드와 같은 작업 ID에서 관련 문서를 갱신합니다.
