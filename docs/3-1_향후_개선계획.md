## 🎯 1. 개발 및 운영 원칙

- 작업 전 `git status --short`와 대상 diff를 확인하고 사용자 미커밋 변경을 보존합니다.
- 새 서비스·서버형 DB·외부 의존성보다 기존 서비스 계층, SQLite 헬퍼와 표준 라이브러리를 우선합니다.

## 🚀 2. 주요 개선 과제 (Backlog)

### 📱 사용자 모바일 UI 개선 정책

- **목표 사용자**: `STAFF`, `TEAM_LEAD`, `PM`이 휴대전화에서 로그인, 연차 신청, 신청 내역 확인·취소, 팀 일정 조회와 결재를 완료할 수 있어야 합니다.
- **관리자 범위**: `ADMIN` 모바일은 대시보드와 주요 현황을 조회할 수 있는 수준까지만 보장합니다. 사원·공휴일·설정·감사·연차 데이터의 등록, 수정, 삭제와 대량 처리는 PC 사용을 기준으로 하며 모바일 기능 동등성은 목표로 하지 않습니다.
- **구현 원칙**:
  - 외부 UI 라이브러리나 별도 모바일 앱을 도입하지 않고 현재 Jinja2, Tailwind CSS와 브라우저 기본 입력 요소를 우선 사용합니다.
  - CSS의 `hidden`만으로 데스크톱 대형 DOM을 숨기는 방식은 모바일 경량화로 간주하지 않습니다.
  - 사용자 화면의 모바일 분기점은 현재 템플릿 기준인 `md` 또는 `lg`를 유지하되, 한 화면 안에서 상충하는 분기점 사용은 정리합니다.
  - 업무 규칙과 API 계약은 유지하고 표시·탐색·전송량을 우선 개선합니다.

### 🔴 [P1] High — 사용자 모바일 핵심 흐름

#### [MOB-001] 로그인 후 공통 상단바 반응형 정비

| 항목 | 내용 |
|---|---|
| 상태 | 대기 |
| 대상 사용자 | `STAFF`, `TEAM_LEAD`, `PM` 필수, `ADMIN` 공통 적용 |
| 대상 경로 | 로그인 후 `base.html`을 사용하는 전체 화면 |
| 관련 파일 | `src/templates/base.html`, `src/app/main.py`, `src/app/routers/admin/settings.py` |

- **현상 및 영향**
  - 상단 브랜드 링크가 `shrink-0`, 계정 작업 영역이 `flex-shrink-0`으로 동시에 고정되어 있습니다.
  - 알림, `비밀번호 변경`, `로그아웃`이 한 줄에 전체 문구로 노출되어 320~390px 화면에서 브랜드 영역과 충돌할 수 있습니다.
  - `product_nav_short`가 비어 있으면 긴 `product_display_name`이 상단 이름으로 대체되므로 브랜딩 설정에 따라 문제가 확대됩니다.
  - 상단 이름 또는 계정 작업이 잘리거나 본문에 가로 스크롤이 생겨 필수 계정 기능의 터치 위치가 불안정해질 수 있습니다.
- **기술 원인**
  - 브랜드 링크에 축소 가능한 최대 폭이 없고 텍스트의 `truncate`가 동작할 명시적 폭 제약이 없습니다.
  - 모바일 전용 계정 메뉴 또는 축약 표현이 없으며 데스크톱 작업 문구를 그대로 사용합니다.
- **구현 요구사항**
  1. 모바일 브랜드 영역에 `min-w-0`와 최대 폭을 부여하고 긴 이름은 한 줄 말줄임 처리합니다.
  2. 알림 버튼은 유지하되 비밀번호 변경과 로그아웃은 하나의 계정 메뉴 또는 의미가 명확한 아이콘·짧은 문구로 묶습니다.
  3. 계정 메뉴는 키보드 포커스, 바깥 영역 클릭, `Escape` 닫기를 지원하고 기존 `window.shimModal` 비밀번호 변경 흐름을 재사용합니다.
  4. 알림 드롭다운과 계정 메뉴는 `max-width: calc(100vw - 2rem)` 범위 안에서 표시합니다.
  5. 데스크톱 상단바의 현재 동작과 관리자 페이지 링크는 유지합니다.
- **제외 범위**
  - 브랜딩 저장 규칙, 인증 쿠키, 알림 API와 비밀번호 변경 API는 변경하지 않습니다.
  - 별도 햄버거 메뉴 라이브러리를 추가하지 않습니다.
- **수용 기준**
  - 320px, 360px, 390px, 412px 너비에서 `document.documentElement.scrollWidth === document.documentElement.clientWidth`를 만족합니다.
  - 공식 이름 120자, 상단 짧은 이름 80자, 배지 24자 입력 시에도 알림과 계정 메뉴가 화면 밖으로 밀리지 않습니다.
  - 비밀번호 변경, 로그아웃, 알림 확인을 모바일에서 각각 두 번 이하의 터치로 실행할 수 있습니다.
  - 768px 이상에서는 기존 데스크톱 문구와 배치를 유지합니다.
- **검증 시나리오**
  1. 기본 브랜딩과 최대 길이 브랜딩을 각각 저장한 테스트 DB로 로그인합니다.
  2. 네 가지 기준 너비와 가로 방향에서 상단바의 가로 스크롤, 잘림, 메뉴 위치를 확인합니다.
  3. 알림 드롭다운과 계정 메뉴를 연속으로 열고 닫아 중첩·화면 이탈 여부를 확인합니다.
  4. 키보드 `Tab`, `Enter`, `Escape`로 메뉴와 비밀번호 변경 모달을 조작합니다.

#### [MOB-002] 모바일 팀 일정 월 이동 및 날짜 정합성 보장

| 항목 | 내용 |
|---|---|
| 상태 | 대기 |
| 대상 사용자 | 팀 또는 프로젝트 캘린더 조회 권한이 있는 `STAFF`, `TEAM_LEAD`, `PM` |
| 대상 경로 | `GET /user/team-calendar` |
| 관련 파일 | `src/templates/user_team_calendar.html`, `src/app/routers/api_user.py` |

- **현상 및 영향**
  - 모바일 화면에는 일 단위 이전·다음 버튼만 있고 이전 달, 다음 달 또는 연·월 선택 UI가 없습니다.
  - 초기 일자는 조회 중인 연·월과 관계없이 클라이언트의 오늘 일자 `new Date().getDate()`로 설정됩니다.
  - `오늘로` 버튼도 조회 중인 연·월은 유지한 채 오늘의 일자 숫자만 대입합니다.
  - 현재 일자가 29~31일일 때 더 짧은 달을 직접 조회하면 존재하지 않는 날짜 라벨 또는 빈 목록이 표시될 수 있습니다.
- **기술 원인**
  - 서버가 제공하는 `year`, `month` 조회 기능이 데스크톱 컨트롤에만 연결되어 있습니다.
  - `selectedMobileDayG` 초기화와 `오늘로` 동작에 조회 연·월 비교 및 일자 상한 보정이 없습니다.
- **구현 요구사항**
  1. 모바일 날짜 슬라이더에 이전 달·다음 달 이동을 추가하고 1월↔12월 이동 시 연도를 함께 보정합니다.
  2. 필요하면 기존 `year_options`를 재사용한 연도·월 선택기를 제공하되 새 캘린더 라이브러리는 도입하지 않습니다.
  3. 조회 연·월이 사업장 기준 현재 연·월이면 초기 일자를 오늘로 설정하고, 다른 달이면 1일 또는 명시한 안전한 기본일을 사용합니다.
  4. 모든 일자 변경 후 `1 <= selectedMobileDayG <= totalDaysInMonth` 불변식을 보장합니다.
  5. `오늘로`는 조회 URL 자체를 사업장 기준 현재 연·월로 이동한 뒤 오늘을 선택합니다.
  6. 월 이동 URL은 기존 `year`, `month` 파라미터를 사용하고 접근 권한과 공유 범위 규칙을 변경하지 않습니다.
- **제외 범위**
  - 팀 캘린더 공유 범위, 정렬 정책, 연차 상태 계산과 승인 규칙은 변경하지 않습니다.
  - 모바일에서 데스크톱 월간 타임라인 표를 그대로 축소 표시하지 않습니다.
- **수용 기준**
  - 2026년 1월에서 이전 달 이동 시 2025년 12월, 2026년 12월에서 다음 달 이동 시 2027년 1월이 표시됩니다.
  - 2025년 2월은 28일, 2024년 2월은 29일까지만 이동할 수 있습니다.
  - 현재 날짜가 31일인 환경에서 2월을 열어도 유효한 날짜만 표시됩니다.
  - 다른 달에서 `오늘로`를 누르면 실제 사업장 기준 오늘의 연·월·일로 이동합니다.
  - 표시 날짜와 부재자 목록의 조회 키가 항상 일치합니다.
- **검증 시나리오**
  1. `?year=2025&month=2`, `?year=2024&month=2`, `?year=2026&month=1`, `?year=2026&month=12`를 직접 엽니다.
  2. 첫날·마지막 날에서 이전/다음 일 버튼을 반복 조작합니다.
  3. 현재 달과 과거·미래 달에서 `오늘로`를 비교합니다.
  4. 부재자가 없는 날, 승인된 연차가 있는 날, 결재 대기 건이 있는 날을 각각 확인합니다.

#### [MOB-003] 모바일 신청 내역 연도 탐색 추가

| 항목 | 내용 |
|---|---|
| 상태 | 대기 |
| 대상 사용자 | `STAFF`, `TEAM_LEAD`, `PM` |
| 대상 경로 | `GET /user/history` |
| 관련 파일 | `src/templates/user_history.html`, `src/app/routers/api_user.py` |

- **현상 및 영향**
  - 서버는 `year` 쿼리와 `year_options`를 지원하지만 모바일 카드에는 조회 연도와 연도 선택기가 없습니다.
  - 모바일 사용자는 URL을 직접 수정하지 않으면 과거 연도의 신청 내역과 잔여·사용 통계를 조회할 수 없습니다.
- **구현 요구사항**
  1. 모바일 제목에 `selected_year`를 표시합니다.
  2. 기존 `year_options`를 사용하는 `GET` 연도 선택 폼을 모바일 카드 상단에 추가합니다.
  3. 선택 변경 시 `/user/history?year=YYYY`로 이동하며 기존 서버 조회 로직과 통계 계산을 그대로 재사용합니다.
  4. 해당 연도에 내역이 없어도 연도 선택기, 0건 표시와 연차 통계 카드는 유지합니다.
- **제외 범위**
  - 연도별 할당량 계산, 신청 취소 API, 상태 라벨과 정렬 기준은 변경하지 않습니다.
- **수용 기준**
  - 현재 연도와 과거·미래 할당 연도 사이를 모바일 UI만으로 이동할 수 있습니다.
  - 제목, 총 건수, 통계 카드와 목록이 모두 선택 연도를 기준으로 일치합니다.
  - 선택 연도에 데이터가 없을 때 빈 상태가 표시되고 다른 연도로 다시 이동할 수 있습니다.
- **검증 시나리오**
  1. 신청 데이터가 있는 연도와 없는 연도를 번갈아 선택합니다.
  2. `PENDING`, `APPROVED`, `REJECTED`, `CANCELED` 상태 카드 표시를 확인합니다.
  3. 결재 대기 건 취소 후 같은 연도와 통계가 유지되는지 확인합니다.

#### [MOB-004] 모바일 초기 응답과 DOM 경량화

| 항목 | 내용 |
|---|---|
| 상태 | 대기 |
| 대상 사용자 | `STAFF`, `TEAM_LEAD`, `PM` |
| 대상 경로 | `GET /user/calendar`, `GET /user/team-calendar` |
| 관련 파일 | `src/templates/user_calendar.html`, `src/templates/user_team_calendar.html`, `src/app/routers/api_user.py` |

- **측정 기준선**
  - 2026-07-26 로컬 테스트 데이터 기준 `/user/team-calendar` HTML 응답은 약 744,192바이트였습니다.
  - 같은 응답에 `<td>` 561개, `<button>` 29개, `<script>` 13개가 포함되었습니다.
  - 모바일에서는 일별 부재자 목록만 표시하지만 숨겨진 데스크톱 타임라인 표와 모바일용 JavaScript 데이터가 함께 전송됩니다.
- **현상 및 기술 원인**
  - `hidden lg:flex`는 표시만 숨기므로 모바일 브라우저도 데스크톱 표와 연간 캘린더 DOM을 다운로드·파싱합니다.
  - 같은 연차 데이터가 Jinja2 데스크톱 마크업과 모바일 JavaScript 객체에 중복 직렬화됩니다.
  - 사용자·연차 데이터가 증가할수록 휴대전화의 초기 렌더링, 메모리 사용과 스크롤 응답이 악화될 수 있습니다.
- **구현 요구사항**
  1. 모바일과 데스크톱 데이터 표현을 한 응답에 완전 중복 렌더링하지 않는 구조로 전환합니다.
  2. 사용자 에이전트 문자열에 의존한 서버 분기는 피하고, 가벼운 공통 셸을 먼저 렌더링한 뒤 뷰포트에 필요한 데이터·부분 화면만 불러오는 방식을 우선 검토합니다.
  3. 기존 FastAPI 라우터와 소규모 JSON/부분 HTML 패턴을 재사용하며 새 프런트엔드 프레임워크는 도입하지 않습니다.
  4. 팀 일정 모바일 데이터는 선택한 연·월과 화면에 필요한 사용자 필드만 포함합니다.
  5. 개인 캘린더의 데스크톱 연간 12개월 DOM은 모바일 진입 시 생성하지 않거나 사용자가 달력 보기를 요청할 때 지연 생성합니다.
  6. 로딩, 빈 결과, 권한 없음과 네트워크 실패 상태를 화면에 명시합니다.
- **단계적 구현 권장**
  1. 응답 크기와 주요 DOM 개수를 측정하는 재현 검사를 먼저 고정합니다.
  2. `/user/team-calendar`의 중복 데이터 제거를 우선 적용합니다.
  3. `/user/calendar`의 데스크톱 연간 DOM 지연 렌더링을 적용합니다.
  4. 실제 사용자 수 규모의 테스트 데이터로 전후 수치를 비교합니다.
- **제외 범위**
  - 서비스 워커, 오프라인 캐시, SPA 전환과 신규 JavaScript 프레임워크 도입은 포함하지 않습니다.
  - 체감 근거 없이 범용 캐시 계층을 추가하지 않습니다.
- **수용 기준**
  - 기준 테스트 데이터에서 모바일 팀 일정 최초 화면에 숨겨진 500개 이상의 데스크톱 표 셀이 생성되지 않습니다.
  - `/user/team-calendar` 초기 HTML 크기를 기준선 대비 60% 이상 줄입니다.
  - 같은 데이터가 데스크톱 마크업과 모바일 데이터 객체에 이중 포함되지 않습니다.
  - 360px 모바일 화면에서 로딩 중 조작 불능이나 큰 레이아웃 이동 없이 일별 목록을 표시합니다.
  - 데스크톱 타임라인의 정렬, 상세 팝업과 기간 선택 기능은 회귀하지 않습니다.
- **검증 시나리오**
  1. 현재 `seed_test_data.py` 수준과 사용자 수를 확대한 데이터에서 응답 바이트와 DOM 개수를 비교합니다.

  3. 모바일·데스크톱에서 같은 날짜의 부재자와 연차 시간이 일치하는지 비교합니다.
  4. JavaScript 로딩 실패 시 빈 흰 화면 대신 오류·재시도 상태가 표시되는지 확인합니다.

#### [MOB-005] 모바일 개인 월간 캘린더 제공

| 항목 | 내용 |
|---|---|
| 상태 | 대기 |

| 대상 경로 | `GET /user/calendar` |
| 관련 파일 | `src/templates/user_calendar.html`, `src/app/routers/api_user.py` |

- **현상 및 영향**
  - 모바일 `/user/calendar`는 현황, 퀵 액션, 간편 신청과 최근 내역만 제공하고 실제 월간 달력은 표시하지 않습니다.
  - 날짜 입력으로 신청은 가능하지만 월간 연차 배치, 공휴일과 주말을 확인하면서 날짜를 선택할 수 없습니다.
- **구현 요구사항**
  1. 모바일에 한 달 단위의 7열 축약 달력을 제공합니다.
  2. 이전·다음 달 이동과 연도 변경은 기존 `selected_year`, `month_calendar_meta`, `holiday_map`을 재사용합니다.
  3. 근무일 선택 시 기존 모바일 간편 신청 폼의 시작일·종료일을 채우고 폼으로 스크롤하거나 신청 패널을 엽니다.
  4. 주말·공휴일은 선택 불가 상태와 이름을 시각적으로 구분합니다.
  5. 승인, 결재 대기, 공가/출장은 색상만이 아니라 짧은 텍스트 또는 범례로 함께 구분합니다.
- **제외 범위**
  - 외부 달력 컴포넌트, 드래그 선택과 모바일에서의 연간 12개월 동시 표시는 도입하지 않습니다.
- **수용 기준**
  - 320px 화면에서 일곱 열이 가로 스크롤 없이 표시됩니다.
  - 날짜 셀을 누르면 선택 날짜가 간편 신청 폼에 정확히 반영됩니다.
  - 주말·공휴일은 신청할 수 없고 기존 서버 검증과 결과가 일치합니다.
  - 이전·다음 달 이동 시 연도 경계와 선택 상태가 정확히 갱신됩니다.
- **검증 시나리오**
  1. 28·29·30·31일 달과 일요일·월요일 시작 달을 각각 확인합니다.
  2. 공휴일, 주말, 기존 연차가 있는 날과 빈 근무일을 선택합니다.
  3. 한 날짜 신청과 시작·종료일 범위 신청을 완료합니다.

#### [MOB-006] 모바일 가독성·터치 영역·긴 텍스트 정비

| 항목 | 내용 |
|---|---|
| 상태 | 대기 |
| 대상 사용자 | `STAFF`, `TEAM_LEAD`, `PM` |
| 대상 경로 | 사용자 캘린더, 팀 일정, 신청 내역, 결재 관리, 공통 모달 |
| 관련 파일 | `src/templates/base.html`, `src/templates/user_*.html`, `src/templates/partials/user_*.html` |

- **현상 및 영향**
  - 모바일 전용 화면에 8~10px 보조 글자, 높이 약 32px인 날짜 이동·상태·결재 버튼과 작은 체크박스가 반복됩니다.
  - 팀 일정의 사용자명, 팀명, 시간대와 최대 500자 신청 사유에 `min-w-0`, 줄바꿈 또는 표시 상한이 일관되게 적용되지 않습니다.
  - 마우스 `title`에 의존하는 상세 설명은 터치 화면에서 확인하기 어렵습니다.
- **구현 요구사항**
  1. 주요 본문과 조작 라벨은 12px 이상, 핵심 정보는 14px 이상을 기본으로 정리합니다.
  2. 날짜 이동, 제출, 취소, 승인·반려 등 핵심 터치 대상은 가능한 범위에서 최소 44×44px 조작 영역을 확보합니다.
  3. 작은 시각 요소를 유지해야 하면 버튼 패딩 또는 투명 클릭 영역으로 터치 크기를 보완합니다.
  4. 가변 텍스트를 담는 flex/grid 자식에 `min-w-0`, `break-words` 또는 `overflow-wrap`을 적용합니다.
  5. 신청 사유는 무제한 한 줄 확장 대신 합리적인 줄 수로 표시하고 전체 내용 확인 수단을 제공합니다.
  6. 상태는 색상만으로 구분하지 않고 현재 텍스트 라벨을 유지합니다.
  7. Tailwind 빌드 결과에 존재하지 않는 비표준 클래스가 있으면 지원되는 유틸리티 또는 임의값으로 교체합니다.
- **제외 범위**
  - 전체 디자인 시스템 교체, 다크 모드와 새로운 아이콘 패키지는 포함하지 않습니다.
- **수용 기준**
  - 320px 화면에서 긴 한글·영문·공백 없는 문자열 때문에 상태 배지나 버튼이 화면 밖으로 밀리지 않습니다.
  - 모바일 핵심 작업 버튼은 인접 버튼과 오동작 없이 터치할 수 있습니다.
  - 브라우저 글꼴 확대 200%에서도 신청, 취소와 월 이동 기능에 접근할 수 있습니다.
  - 키보드 포커스 표시와 상태 텍스트가 유지됩니다.
- **검증 시나리오**
  1. 사용자명·회사명·팀명을 각 필드 최대 길이로 입력한 테스트 데이터를 사용합니다.
  2. 한글 500자, 공백 없는 영문 500자와 URL 형태의 신청 사유를 각각 표시합니다.
  3. 320px·360px 화면과 글꼴 확대 200%에서 줄바꿈, 버튼 겹침과 가로 스크롤을 확인합니다.
  4. 팀장 계정으로 모바일 승인·반려·일괄 선택을 실제 테스트 데이터에서 수행합니다.

- **운영 중인 DB를 위한 안전한 SQLite 스키마 마이그레이션 체계**
  - **배경**: 운영 데이터가 쌓인 뒤 외래키, 인덱스 또는 중요 컬럼을 바꿀 상황에 대비합니다.
  - **개선 방향**: SQLite 제약을 고려해 임시 테이블 복사, 재생성, 검증과 실패 시 복구를 자동화합니다.
  - **완료 기준**: 운영 DB 복제본에서 성공·실패·롤백과 데이터 정합성을 검증합니다.
  - **설계 주의**: 실제 스키마 변경 요구 전 범용 프레임워크를 도입하지 않고 첫 실제 마이그레이션과 함께 최소 도구를 설계합니다.

## 📐 5. 모바일 UI 공통 검증 명세

### 5.1 기준 화면

| 구분 | 뷰포트 | 확인 목적 |
|---|---:|---|
| 소형 Android | 320×568 | 최소 너비, 상단바와 폼 가로 넘침 |
| 일반 Android | 360×800 | 기본 모바일 사용 흐름 |

| 대형 Android | 412×915 | 긴 목록과 카드 밀도 |
| 가로 방향 | 844×390 | 화면 회전 후 메뉴·모달·날짜 선택 |

### 5.2 사용자 역할별 필수 흐름

| 역할 | 필수 검증 흐름 |
|---|---|
| `STAFF` | 로그인 → 연차 신청 → 신청 내역 확인 → 결재 대기 건 취소 → 팀 일정 조회 |
| `TEAM_LEAD` | `STAFF` 흐름 → 모바일 결재 목록 조회 → 단건 승인·반려 → 일괄 결재 |
| `PM` | 프로젝트 범위 팀 일정 조회 → 본인 자동 승인 신청 → 결재 대상 범위 확인 |
| `ADMIN` | 로그인 → 대시보드 조회 → 공통 상단바 계정 작업 확인. 모바일 관리 기능 동등성은 검사하지 않음 |

### 5.3 공통 합격 조건

1. 의도하지 않은 본문 가로 스크롤이 없습니다.
2. 고정·드롭다운·모달 요소가 뷰포트 밖으로 이탈하지 않습니다.
3. 모바일 가상 키보드가 열린 상태에서도 현재 입력과 제출·취소 버튼에 접근할 수 있습니다.
4. 날짜·시간·통계·상태 값은 같은 조건의 데스크톱 화면과 일치합니다.
5. 주말, 공휴일, 중복 신청, 잔여 연차 부족과 결재 권한 오류가 기존 서버 규칙대로 처리됩니다.
6. 모바일 전용 개선이 데스크톱 UI와 포터블·폐쇄망 실행을 깨지 않습니다.
7. 최소 회귀 검사는 기존 smoke 테스트와 함께 실행하며, 레이아웃은 기준 화면에서 수동 확인 증적을 남깁니다.

### 5.4 실행 및 확인 절차

```powershell
npm run dev
```

- 개발 서버가 출력한 URL에 접속해 브라우저 개발자 도구의 기기 모드를 사용합니다.
- 기본 포트 사용이 불가능하면 다음처럼 사용 가능한 포트를 지정합니다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\scripts\dev.ps1 -Port 9183
```

- 연도·월 경계 검증 URL 예시는 다음과 같습니다.

```text
/user/history?year=2025
/user/team-calendar?year=2025&month=2
/user/team-calendar?year=2024&month=2
/user/team-calendar?year=2026&month=1
/user/team-calendar?year=2026&month=12
```

- 자동 브라우저 회귀 도구는 반복적인 모바일 회귀가 실제로 발생하거나 수동 검증 비용이 커질 때 도입을 재검토합니다. 그 전에는 새 의존성 없이 기존 테스트와 위 수동 검증표를 사용합니다.

## 🛠️ 6. 모바일 UI 단계별 구현계획

이 절은 `MOB-001`~`MOB-006`을 나중에 바로 착수할 수 있도록 작업 순서, 구현 경계, 인터페이스와 검증 게이트를 고정합니다. 개별 요구사항과 수용 기준은 2절의 각 작업 정의를 기준으로 하며 이 절에서는 중복 기술하지 않습니다.

### 6.1 구현 원칙과 상태 관리

- 작업 순서는 `P1 → P2`로 고정합니다.
- 상태는 `대기 → 진행 중 → 검증 대기 → 완료 이관` 순서로 관리합니다.
- 한 번에 하나의 작업 ID만 `진행 중`으로 변경하고 검증 게이트를 통과한 뒤 다음 작업을 시작합니다.
- 새 UI 프레임워크, 서비스 워커, 사용자 에이전트 기반 서버 분기와 범용 캐시는 도입하지 않습니다.
- `ADMIN` 모바일은 대시보드와 주요 현황 조회까지만 보장하고 등록·수정·삭제·대량 처리는 PC 사용을 기준으로 합니다.
- 각 작업 시작 전에 `git status --short`와 대상 파일 diff를 확인해 사용자 미커밋 변경을 보존합니다.
- 데이터베이스 스키마, 기존 연차 신청·취소 API와 역할별 업무 규칙은 변경하지 않습니다.

### 6.2 P1 작업 패키지

| 순서 | 작업 | 주요 변경 위치 | 구현 결과 | 종료 게이트 |
|---:|---|---|---|---|
| 1 | `MOB-001` | `src/templates/base.html` | 모바일 계정 메뉴, 상단바 축소·말줄임, 접근성 동작 | 320px에서 가로 넘침 없음 |
| 2 | `MOB-002` | `src/templates/user_team_calendar.html`, `src/app/routers/api_user.py` | 서버 업무일 기준 월·일 이동과 날짜 보정 | 윤년·연도 경계 통과 |
| 3 | `MOB-003` | `src/templates/user_history.html` | 모바일 연도 선택과 선택 연도 표시 | 데이터 유무 연도 모두 조회 가능 |
| 4 | `MOB-004` | 사용자 캘린더 템플릿, `src/app/routers/api_user.py` | 공통 셸과 화면별 부분 지연 로딩 | 모바일 초기 HTML 60% 이상 감소 |

#### 6.2.1 구현 결정

1. `MOB-001`
   - 모바일에서는 알림 버튼을 유지하고 비밀번호 변경·로그아웃을 하나의 44×44px 계정 메뉴로 묶습니다.
   - PC에서는 현재 텍스트 버튼을 유지합니다.
   - 계정 메뉴에 `aria-expanded`, 바깥 영역 클릭 닫기와 `Escape` 닫기를 적용하고 기존 `window.shimModal`을 재사용합니다.
2. `MOB-002`
   - 서버 업무일 ISO 문자열을 `business_today`로 전달합니다.
   - 선택 연·월이 업무일과 같으면 오늘, 다르면 1일로 초기화하고 모든 이동 뒤 해당 월의 마지막 일자 이내로 보정합니다.
   - `오늘로`는 일자 숫자만 바꾸지 않고 업무일의 연·월 URL로 이동합니다.
   - 1월 이전과 12월 다음 이동 시 연도를 함께 변경합니다.
3. `MOB-003`
   - 기존 `year_options`를 사용하는 네이티브 `GET` 연도 선택기를 모바일 카드 상단에 추가합니다.
   - 선택 연도는 제목, 총 건수, 통계, 목록과 빈 상태에 동일하게 적용합니다.
4. `MOB-004`
   - 다음 부분 템플릿을 생성합니다.
     - `src/templates/partials/user_calendar_desktop.html`
     - `src/templates/partials/user_team_calendar_desktop.html`
   - 기본 사용자 페이지는 공통 레이아웃과 모바일 셸만 먼저 렌더링합니다.
   - `matchMedia('(min-width: 1024px)')`로 PC에서는 부분 HTML, 모바일에서는 JSON만 한 번 불러옵니다.
   - 팀 캘린더 권한·공유 범위 계산은 `_build_team_calendar_context` 형태의 공통 내부 함수로 추출해 HTML과 JSON이 같은 결과를 사용하게 합니다.
   - 동적 사용자명·팀명·회사명·시간대·사유는 문자열 `innerHTML` 조합 없이 DOM 노드와 `textContent`로 출력합니다.
   - 로딩 중 진행 상태, 빈 결과, 실패 문구와 재시도 버튼을 모두 제공합니다.

### 6.3 P2 작업 패키지

| 순서 | 작업 | 주요 변경 위치 | 구현 결과 | 종료 게이트 |
|---:|---|---|---|---|
| 5 | `MOB-005` | `src/templates/user_calendar.html`, `src/app/routers/api_user.py` | 모바일 한 달 캘린더와 기존 신청·상세 모달 연결 | 신청·조회·취소 모바일 완료 |
| 6 | `MOB-006` | 공통·사용자 템플릿, Tailwind 산출물 | 글자·터치·줄바꿈·배너 정비 | 전체 기준 화면 통과 |

#### 6.3.1 구현 결정

1. `MOB-005`
   - 빠른 신청 카드는 모바일 캘린더 위에 유지합니다.
   - 모바일에는 선택 월 한 달만 7열로 렌더링하고 12개월 전체 DOM은 생성하지 않습니다.
   - 연·월 선택과 이전·다음 달 이동은 월간 JSON을 다시 조회하고 `history.replaceState`로 URL의 `year`, `month`를 동기화합니다.
   - 빈 근무일은 기존 신청 모달, 기존 신청일은 상세·취소 모달을 엽니다.
   - 주말과 공휴일은 선택할 수 없으며 상태를 색상과 텍스트로 함께 표시합니다.
2. `MOB-006`
   - 핵심 터치 영역은 최소 44×44px, 주요 본문은 14px, 보조 정보는 12px 이상을 기준으로 합니다.
   - 가변 텍스트 영역에 `min-w-0`, 줄바꿈과 최대 표시 범위를 적용합니다.
   - 긴 사유는 요약하고 `전체 보기` 동작을 제공합니다.
   - 마우스 `title`이나 호버에만 의존하는 정보는 탭 또는 모달로 확인할 수 있게 합니다.
   - 기본 비밀번호 안내 배너는 모바일에서 세로 배치하고 작업 버튼의 터치 영역을 확보합니다.
   - 지원되지 않는 Tailwind 유틸리티를 제거한 뒤 `npm run build:css`로 CSS 산출물을 다시 생성합니다.

### 6.4 구현 인터페이스 계약

#### 6.4.1 추가 엔드포인트

| 메서드와 경로 | 응답 | 용도 |
|---|---|---|
| `GET /user/calendar/desktop-partial?year=YYYY` | HTML 부분 화면 | PC 개인 연간 캘린더 지연 로딩 |
| `GET /user/team-calendar/desktop-partial?year=YYYY&month=M&sort=...&sort_dir=...&layout=timeline` | HTML 부분 화면 | PC 팀 타임라인 지연 로딩 |
| `GET /api/user/team-calendar?year=YYYY&month=M` | JSON | 모바일 팀 일정 |
| `GET /api/user/calendar-month?year=YYYY&month=M` | JSON | 모바일 개인 월간 캘린더 |

- 모든 엔드포인트는 기존 로그인, 역할과 팀 공유 범위를 그대로 적용합니다.
- `month`는 `1`~`12`만 허용하고 범위를 벗어나면 HTTP 422를 반환합니다.
- 데이터베이스 스키마와 기존 신청·취소 API는 변경하지 않습니다.

#### 6.4.2 모바일 팀 일정 JSON

```json
{
  "year": 2026,
  "month": 7,
  "days_in_month": 31,
  "business_today": "2026-07-26",
  "days": {
    "1": [
      {
        "user_name": "사용자명",
        "team": "팀명",
        "company": "회사명",
        "status": "APPROVED",
        "is_deductive": true,
        "deduction_hours": 8.0,
        "slot_label": "09:00~18:00",
        "reason": "사유"
      }
    ]
  }
}
```

- 상태 값은 기존 연차 상태 문자열을 사용합니다.
- `days`에는 선택한 연·월과 모바일 일별 목록에 필요한 필드만 포함합니다.

#### 6.4.3 모바일 개인 월간 JSON

```json
{
  "year": 2026,
  "month": 7,
  "days_in_month": 31,
  "offset": 3,
  "business_today": "2026-07-26",
  "holidays": {
    "17": "제헌절"
  },
  "days": {
    "5": [
      {
        "id": 1,
        "status": "PENDING",
        "is_deductive": true,
        "deduction_hours": 8.0,
        "slot_label": "09:00~18:00",
        "reason": "사유",
        "rejection_reason": null
      }
    ]
  }
}
```

- `offset`은 월 첫날의 일요일 기준 열 위치 `0`~`6`입니다.
- 휴일과 개인 신청 데이터는 선택한 한 달만 반환합니다.

### 6.5 자동 검증과 실행 명령

`tools/scripts/test_mobile_ui.py` 하나를 추가하고 기존 smoke 실행 목록에 등록합니다. 테스트는 임시 데이터베이스와 기존 FastAPI `TestClient` 패턴을 재사용하며 새 브라우저 테스트 의존성을 추가하지 않습니다.

자동 검증 범위는 다음과 같습니다.

1. 인증되지 않은 부분 HTML·JSON 접근 차단
2. `STAFF`, `TEAM_LEAD`, `PM` 역할별 팀 일정 공개 범위
3. 팀 일정 JSON에서 `ADMIN` 계정 제외
4. 1월↔12월 연도 경계
5. 2024년과 2025년 2월의 윤년 처리
6. `month=0`, `month=13` 요청의 HTTP 422 응답
7. 모바일 셸에 데스크톱 대형 테이블이 포함되지 않음
8. 긴 이름·팀명·사유가 HTML이 아닌 데이터로 안전하게 직렬화됨
9. 사용 이력 제목·건수·통계·목록의 선택 연도 일치

```powershell
npm run build:css
python -m compileall -q src tools portable
python tools/scripts/verify_version_sync.py
python tools/scripts/test_mobile_ui.py
python tools/scripts/run_tests.py smoke
```

### 6.6 수동 검증과 성능 게이트

- 5.1의 320×568, 360×800, 390×844, 412×915와 가로 화면을 모두 확인합니다.
- `STAFF`, `TEAM_LEAD`, `PM`은 신청·조회·취소·팀 일정·권한 범위 흐름을 검증합니다.
- `ADMIN`은 대시보드 조회와 공통 상단바 계정 작업만 검증하며 모바일 관리 기능 동등성은 검사하지 않습니다.
- 브라우저 글꼴 확대 200%에서도 가로 스크롤, 버튼 겹침과 필수 작업 접근 불가가 없어야 합니다.
- `MOB-004` 완료 시 약 744KB 기준 응답과 개선 후 응답의 바이트, `<td>` 개수와 로딩 결과를 함께 기록합니다.
- 모바일 초기 HTML에는 숨겨진 데스크톱 대형 표가 없어야 하며 기준 데이터에서 응답 크기가 60% 이상 감소해야 합니다.
- PC에서는 연간 캘린더, 팀 정렬, 상세 모달과 기간 선택 기능이 기존과 동일하게 동작해야 합니다.

### 6.7 완료, 이관과 복구

- 데이터베이스 변경이 없으므로 별도 마이그레이션과 기능 플래그는 추가하지 않습니다.
- 문제가 발생하면 해당 MOB 작업 단위만 되돌릴 수 있도록 작업 ID별 변경 범위를 유지합니다.
- 구현 또는 검증이 남으면 상태를 `완료 이관`으로 변경하지 않고 차단 사유와 남은 조건을 기록합니다.
- 완료된 MOB 항목은 이 문서에서 제거하고 구현·검증 증적과 성능 전후 수치를 `docs/2-1_운영_릴리즈_통합_산출물.md`로 이관합니다.
- 변경 후 실제 UI 구조와 엔드포인트는 `docs/4-1_SHIM_프로젝트_설계서.md`에 현재 상태로 반영합니다.
- `MOB-001`~`MOB-006`이 모두 이관되면 이 6절도 함께 제거합니다.
