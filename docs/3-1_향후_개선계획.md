# 향후 개선계획 (Product Roadmap)

이 문서는 아직 완료되지 않은 백로그만 관리합니다. 완료된 변경과 검증 증적은 `docs/2-1_운영_릴리즈_통합_산출물.md`, 변경 후의 현재 설계는 `docs/4-1_SHIM_프로젝트_설계서.md`에서 관리합니다.

SHIM은 폐쇄망에서 로컬 Windows, Docker, 포터블 실행을 모두 지원하는 단일 FastAPI·SQLite 애플리케이션입니다. 등록 사용자 수만으로 무거운 보안·관측 인프라를 추가하지 않고, 실제 동시성, 망 신뢰도, 운영 장애 기록과 고객 보안 요구를 근거로 우선순위를 조정합니다.

---

## 🎯 1. 개발 및 운영 원칙

- 기존 테스트·작업 로그·릴리스 증적에서 사용한 작업 ID를 다른 의미로 재사용하지 않습니다.
- 작업 전 `git status --short`와 대상 diff를 확인하고 사용자 미커밋 변경을 보존합니다.
- 새 서비스·서버형 DB·외부 의존성보다 기존 서비스 계층, SQLite 헬퍼와 Python 표준 라이브러리를 우선합니다.
- 로컬 Windows, Docker, 포터블에서 인터넷 없이 동작하는 현재 설계를 유지합니다.
- 공개 상태 점검에는 내부 경로, 예외 원문, 백업 세부 정보와 같은 운영 정보를 노출하지 않습니다.
- Docker 로그는 표준 출력, 포터블 로그는 제한된 순환 파일을 사용합니다.
- 보안 기능은 공격 차단 효과와 함께 관리자 계정 잠금, 서비스 거부, 복구 불가와 같은 역효과도 검증합니다.
- 재현 테스트를 먼저 추가하고 일부 구현이나 검증이 남으면 완료 처리하지 않습니다.
- 여러 개선을 한 번에 묶어 즉시 운영 가능하다고 판단하지 않고, 과제별 표적 테스트와 배포 형태별 검증을 남깁니다.

## 🟡 2. 조건부·후속 개선 과제 (P2)

### [OPS-004] 포터블 장애 분석용 순환 파일 로그

- **근거**: 포터블 마스터와 Uvicorn 작업자는 콘솔 없는 백그라운드 프로세스로 실행되어 장애 출력이 운영자에게 남지 않습니다.
- **개선 방향**:
  - Python 표준 `logging`과 `RotatingFileHandler`를 우선 사용합니다.
  - Docker는 표준 출력 로그를 유지합니다.
  - 포터블 파일 로그는 해석된 `SHIM_DATA_DIR` 아래 `log` 폴더에 두고 작은 용량과 보관 개수 제한을 적용합니다.
  - 포터블 마스터와 Uvicorn 작업자가 같은 순환 파일에 동시에 쓰지 않도록 `shim-master.log`와 `shim-app.log`처럼 파일을 분리합니다.
  - Uvicorn 및 애플리케이션 로거의 파일 작성 주체와 전파 방식을 명시해 같은 사건이 두 파일에 불필요하게 중복 기록되지 않게 합니다.
  - DB 손상·복구, 백업 실패, 인증·기동 실패와 Uvicorn 오류처럼 운영에 필요한 사건부터 전환합니다.
  - 파일 로그 초기화에 실패하면 표준 출력으로 대체하고 앱 기동은 계속합니다.
  - 로그 파일은 `SHIM_DATA_DIR` 아래에서 데이터 폴더의 기존 OS 접근 권한을 상속하고, 애플리케이션이 권한을 더 넓히지 않게 합니다.
  - 첫 구현에서 별도 Windows ACL 조작 코드를 추가하지 않고 운영 문서에서 데이터 폴더 접근 주체를 제한하도록 안내합니다.
- **제외 범위**:
  - 중앙 JSON 로그 수집기가 없는 상태에서 `structlog`와 전면 JSON 로깅을 도입하지 않습니다.
  - 100MB 파일 10개처럼 포터블 환경에 과도한 보관량을 기본값으로 사용하지 않습니다.
- **완료 기준**:
  - 숨김 실행에서 로그 생성, 순환·용량 제한, 재기동, 로그 폴더 생성 실패와 민감정보 비노출을 검증합니다.
  - 마스터와 작업자가 동시에 로그를 기록하고 순환 임계치에 도달해도 Windows 파일 잠금·이름 변경 충돌이나 로그 손실로 프로세스가 중단되지 않음을 검증합니다.
  - 단순 테스트 메시지가 아니라 실제 포터블 기동 실패와 백업 실패를 각각 유도해 원인과 시각이 파일 로그에 남는지 확인합니다.
  - 로그 폴더와 파일이 데이터 폴더의 접근 권한을 상속하고, 생성·순환·재기동 뒤에도 권한이 불필요하게 완화되지 않음을 확인합니다.
  - 포터블 가이드에 로그 경로, 보관 범위와 장애 발생 시 확인 순서를 추가합니다.

### [CI-001] 조건부 지속적 검증 및 의존성 감사

- **착수 조건**: 여러 작업자가 GitHub에서 협업하거나, PR 병합 게이트·반복 배포·빈번한 의존성 변경이 필요해질 때 착수합니다. 데이터 교체 위험이 큰 작업을 시작할 때도 현재 로컬 검증만으로 충분한지 다시 평가합니다.
- **목적**: 보안·운영 변경의 회귀와 신규 의존성 취약점을 GitHub 변경 단계에서 조기에 발견합니다.
- **실행 환경**:
  - 운영 Docker와 동일한 Python 3.12를 기본으로 사용합니다.
  - 날짜 브라우저 회귀 검사와 Node 감사에 필요한 지원 중인 Node.js 버전을 명시적으로 준비합니다.
  - 테스트 의존성은 `requirements-dev.txt`로 설치하고 `pip-audit`은 CI 작업에서만 별도 설치합니다.
- **필수 단계**:
  - Python 전체 컴파일
  - 버전 정합성 검사
  - smoke 테스트
  - `pip-audit -r requirements.txt`
  - Node 의존성을 변경하는 경우 `npm audit`
- **운영 원칙**:
  - CI 도입 전에는 각 과제에서 로컬 `smoke`와 필요한 `release`·배포 형태별 검증을 생략하지 않습니다.
  - 감사와 smoke를 별도 단계로 실행해 실패 원인을 구분합니다.
  - 감사·테스트 명령 뒤에 `|| true`를 붙여 실패를 무시하지 않습니다.
  - 이미 분석하고 수용한 취약점만 식별자와 사유를 명시해 제한적으로 예외 처리합니다.
  - 새 표적 테스트는 파일 생성만으로 끝내지 않고 `tools/scripts/run_tests.py`의 smoke 또는 release 목록에 등록합니다.
  - GitHub Actions 권한은 기본 `contents: read`로 제한하고 쓰기 권한이나 저장소 Secret이 필요한 작업은 별도 근거가 있을 때만 허용합니다.
  - 외부 Action은 검증된 커밋 SHA로 고정하고 자동으로 부유하는 태그를 사용하지 않습니다.
  - `ruff`나 `mypy --strict`는 기존 코드 기준선과 수정 범위가 준비되기 전 필수 게이트로 추가하지 않습니다.
  - Dependabot은 자동 PR을 지속적으로 처리할 담당자가 있을 때만 활성화합니다.
- **완료 기준**:
  - 정상 브랜치에서 모든 필수 단계가 통과합니다.
  - 의도적으로 실패시킨 테스트와 신규 감사 경고가 CI를 실패시키는지 확인합니다.
  - 감사 결과 또는 수용 예외를 릴리스 증적에 기록합니다.

### [DB-001] 조건부 SQLite 스키마 마이그레이션 안전성 보강

- **현재 판단**: 아직 실제 사용자가 없고 보존해야 할 과거 운영 DB도 없으므로 기존 버전 DB를 위한 소급 마이그레이션은 구현하지 않습니다.
- **착수 조건**: 보존해야 할 사용자 데이터가 있는 기존 DB가 생기거나, 배포된 DB의 컬럼·인덱스·외래키를 실제로 변경해야 하는 첫 요구가 발생했을 때 착수합니다.
- **필요해졌을 때의 개선 방향**:
  - 기존 `src/app/migrations.py`의 `schema_versions`, `tools/scripts/db_init.py`의 초기화 잠금과 `src/app/services/ops.py`의 SQLite 백업·검증을 재사용합니다.
  - 기존 DB의 스키마를 변경하기 직전에 일반 순환 대상과 분리된 `pre_migration` 백업을 만들고 검증한 경우에만 변경합니다.
  - 실제 변경에 필요한 버전별·멱등 마이그레이션과 해당 기존 DB 복제본 테스트만 추가합니다.
- **현재 제외 범위**:
  - 사용자가 없는 개발 단계에서 과거 모델의 모든 누락 컬럼을 소급 조사하거나 지원 마이그레이션을 만들지 않습니다.
  - 구체적인 스키마 변경 요구 전에 범용 마이그레이션 프레임워크를 만들지 않습니다.
- **호환 기준**:
  - 현재 개발 버전에서 새로 생성한 DB를 최초 지원 기준선으로 사용하고, 신규 설치는 현재 SQLAlchemy 모델로 생성되는 스키마만 검증합니다.
  - 기준선 이전 개발 DB는 지원 대상에 포함하지 않습니다. 보존할 데이터가 없으면 초기화하고, 보존 요구가 생기면 그 시점에 `DB-001`을 재평가합니다.
- **완료 기준**:
  - 착수 전에는 신규 빈 데이터 디렉터리에서 현재 모델 기준 DB 생성과 기동만 검증합니다.
  - 착수 후에는 실제 지원 대상 기존 DB 복제본에서 성공·실패·재실행·롤백, 행 수, `quick_check`, 외래키, 인덱스와 마이그레이션 버전 정합성을 검증합니다.

### [SEC-004] 통합 유지보수 명령 기반 암호화 키 로테이션

- **착수 조건**: 암호화 모드의 실제 운영 배포에서 키 유출 대응, 정기 교체 정책 또는 고객 보안 요구가 확인됐을 때 착수합니다. 요구가 없으면 문서 정정과 현재 키 보존 원칙만 유지하고 도구를 선제 개발하지 않습니다.
- **목적**: 포터블과 Docker 운영 환경에서 서버를 완전히 종료한 뒤 동일한 코어로 JWT·PII 공용 비밀키를 안전하게 교체합니다.
- **지원 및 배포 원칙**:
  - 소스 실행은 `python -m tools.maintenance`를 사용합니다.
  - Windows 포터블은 기존 `SHIM_Portable.exe maintenance ...` 명령으로 같은 코어를 호출합니다.
  - 사용 편의를 위한 작은 `SHIM_Maintenance.bat` 래퍼는 허용하되 별도 PyInstaller EXE는 실제 독립 실행 요구가 확인될 때만 만듭니다.
  - Linux Docker 호스트는 기존 `shim:<버전>` 앱 이미지에 유지보수 모듈을 포함하고 Uvicorn 대신 유지보수 명령을 실행합니다.
  - 별도 유지보수 OCI 이미지를 만들지 않으며 앱 이미지와 도구의 스키마·버전 불일치를 방지합니다.
  - CPU 지원 범위는 앱 이미지와 동일하게 가져가고, `arm64` 앱 배포 요구가 있을 때 앱과 유지보수 명령을 함께 검증합니다.
- **MVP 필수 명령**:
  - `verify`: DB 무결성, 필수 테이블·컬럼, 현재 키와 `key_hash_snapshot`, 백업 현황과 잔여 WAL/SHM 파일을 변경 없이 검사합니다.
  - `generate-key`: `secrets.token_urlsafe(48)` 기반 신키를 암호화 모드와 호환되는 형식으로 지정 파일에 저장합니다.
  - `rotate-key`: 신키 자동 생성 또는 신키 파일 입력, 롤백 백업, 작업 DB 재암호화, 검증과 설정 교체를 수행합니다.
  - `verify-backup`: 백업과 지정 키를 읽기 전용으로 열어 SQLite·스키마·행 수·암호문 정합성을 검사합니다.
- **후속 부가 명령**:
  - `verify --report <파일>`: 앱·도구·스키마 버전, 운영체제·CPU, DB 무결성, 축약 키 지문, 백업 개수·최근 시각과 WAL/SHM 크기만 담은 진단 보고서를 선택적으로 생성합니다.
  - `reset-admin-password`: 기존 소스 스크립트와 포터블 `--reset-admin`을 통합하고 숨김 입력·재확인·비밀번호 정책·사전 백업·세션 무효화·민감정보 없는 감사 기록을 적용합니다.
  - 후속 부가 명령은 MVP 키 로테이션의 완료를 막지 않고 별도 표적 테스트와 완료 증적을 남깁니다.
- **요구 발생 시 명령**:
  - `enable-encryption`: 평문 설치본을 암호화 모드로 전환해야 하는 실제 요구가 있을 때만 별도 명령으로 추가합니다.
  - `restore-backup`: 현재 시작 시 자동 복구만으로 해결할 수 없는 수동 복원 요구가 확인될 때만 추가합니다. 선택 백업 검증, `pre_restore` 백업과 명시적 `RESTORE` 확인을 필수로 합니다.
- **입력 및 키 원칙**:
  - 포터블은 `--data-dir`과 `--key-file`, Docker는 해석된 `--data-dir`, `--env-file`과 필요한 경우 `--deployment-dir`을 명시합니다.
  - Docker 호스트 경로는 추측하지 않고 `docker compose config` 결과로 확인합니다. 데이터가 배포 루트 밖에 있으면 별도 마운트합니다.
  - Docker 유지보수 명령에는 `docker compose config`로 확인한 실제 Compose 해석 결과의 현재 키를 전달하고, 명시적으로 선택·마운트한 `.env`의 키 지문과 비교합니다. 두 지문이 다르면 출처를 추측하지 않고 변경 전에 중단합니다.
  - 도구가 호스트 셸, Compose override와 다중 `--env-file`의 출처·우선순위를 역추적하지 않습니다. 운영 절차에서 호스트 `SHIM_SECRET_KEY`를 비우고 하나의 명시적 환경 파일만 사용하도록 통제합니다.
  - 설정 교체 뒤 최종 재기동 전에 다음 Compose 해석 결과의 키 지문이 갱신된 DB의 `key_hash_snapshot`과 일치하는지 다시 확인합니다.
  - `--key-file`과 `--env-file`은 동시에 허용하지 않습니다.
  - 키 원문을 명령행 인자로 받거나 로그·보고서에 출력하지 않습니다.
  - 신키를 지정하지 않으면 안전한 랜덤 키를 자동 생성하고 조직 발급 키는 `--new-key-file`로만 입력받습니다.
  - Docker Compose `.env` 해석 차이를 막기 위해 신키는 자동 생성 키와 같은 URL-safe 단일행 형식(`A-Z`, `a-z`, `0-9`, `_`, `-`)으로 제한합니다.
  - 신키는 빈 값, 알려진 공개 기본키, 다중 값과 지나치게 짧은 값을 거부합니다.
  - `generate-key`는 기존 파일을 덮어쓰지 않고 대상이 존재하면 중단합니다.
  - `rotate-key`는 `key_hash_snapshot == "PLAINTEXT_MODE"`인 설치본을 거부하고 평문→암호화 전환은 조건부 `enable-encryption`으로만 수행합니다.
  - 앱 이미지·유지보수 도구와 DB 스키마 버전의 지원 범위를 확인하고, DB가 도구보다 새롭거나 필수 마이그레이션이 누락됐으면 변경 전에 중단합니다.
- **암호화 대상 원칙**:
  - SQLAlchemy 모델 메타데이터를 재암호화 대상의 단일 기준으로 사용하고 `EncryptedString` 컬럼, 기본키와 NULL 허용 여부를 발견합니다.
  - 최초 대상은 `users.user_name`, `leaves.rejection_reason`, `leaves.reason`, `audit_logs.actor_name`입니다.
  - 모델 메타데이터와 읽기 전용으로 조회한 실제 DB 컬럼·지원 스키마가 다르면 변경 전에 중단합니다.
  - 암호문 읽기·갱신은 ORM 값 변환을 거치지 않는 원시 SQL로 수행하되 대상 발견 규칙은 모델 메타데이터에서 중복 관리하지 않습니다.
  - 대상 추가는 모델과 로테이션·백업 검증 테스트를 같은 작업에서 갱신한 경우에만 허용합니다.
- **실행 및 복구 인터페이스**:
  - `rotate-key`는 대상 절대경로, DB 해시, 현재·신규 축약 키 지문, 생성할 롤백 위치와 예상 필요 공간을 먼저 표시하고 대화형 `ROTATE` 확인 후 변경합니다.
  - 비대화형 실행은 모든 경로를 명시하고 `--yes`를 추가한 경우만 허용합니다.
  - 미완료 작업을 자동 추측하지 않고 상태 파일을 지정하는 `--resume <상태파일>`과 `--rollback <상태파일>`로 재개와 원복을 구분합니다.
  - 성공, 입력 오류, 검증 실패, 변경 없음, 복구 필요 상태를 자동화에서 구분할 수 있는 안정적인 종료 코드를 정의합니다.
- **롤백 자료 보관 원칙**:
  - 로테이션 전 DB, 구키와 설정 사본은 파일 해시·축약 키 지문·작업 ID를 담은 매니페스트로 한 세트임을 식별합니다.
  - DB 롤백본은 데이터 보호 경로, 구키와 `.env` 사본은 해당 운영체제에서 접근 권한을 제한할 수 있는 보호 경로에 저장하고 보고서에는 키 원문을 남기지 않습니다.
  - Docker에서 설정 백업을 앱 데이터 마운트 안에 임의 저장하지 않으며, 유지보수 컨테이너에는 확인된 데이터·배포·롤백 경로만 마운트합니다.
- **자동복구 연계 원칙**:
  - 현재 `verify_and_recover_db`가 SQLite 무결성만으로 최신 백업을 선택하는 동작을 보강해, 백업 내부 `key_hash_snapshot`과 현재 활성 키 지문이 일치하는 백업만 자동복구 후보로 허용합니다.
  - 키가 다른 과거 백업은 구키를 명시한 `verify-backup`으로만 검사하며 신키 환경에서 자동복원하지 않습니다.
  - `system_settings` 또는 `key_hash_snapshot`이 없는 레거시 백업은 자동복구 후보에서 제외하고, 구키를 명시하는 `verify-backup`으로만 평가합니다.
  - 키 교체 완료 직후 신키와 갱신된 `key_hash_snapshot`을 포함한 정상 백업을 최소 1개 생성하고 검증한 뒤 서비스 재기동을 완료합니다.
  - 현재 키와 호환되는 정상 백업이 없으면 손상 DB를 보존한 채 중단하고 임의로 구키 백업을 복원하지 않습니다.
- **잠금 및 정지 확인 원칙**:
  - 현재 `DBInitLock`은 초기화 동안만 사용하고 10분 경과 시 강제 제거하므로 장시간 키 로테이션 잠금으로 그대로 재사용하지 않습니다.
  - 공용 잠금은 유지보수 중 새 앱 기동을 막아야 하며, 경과 시간만으로 활성 잠금을 제거하지 않습니다. 비정상 종료 잠금은 운영자가 관련 프로세스가 없음을 확인한 뒤 명시적으로 정리합니다.
  - 포터블 유지보수는 EXE 위치가 아니라 해석된 데이터 디렉터리를 기준으로 앱과 같은 뮤텍스를 확인·획득하고, 명령 분기 직후 DB 모듈 import나 파일 쓰기보다 먼저 수행합니다.
  - Docker·소스 실행의 앱 중지는 운영 절차의 필수 사전조건입니다. SQLite 독점 연결과 WAL 체크포인트는 보조 확인일 뿐 앱 종료의 증명으로 사용하지 않습니다.
- **안전한 처리 순서**:
  1. 입력 경로를 절대경로로 해석하고 기존 DB·설정 파일 존재, 지원 스키마, 허용된 작업 범위와 파일 권한을 확인합니다. `verify`는 데이터 디렉터리를 만들 수 있는 DB·모델 모듈을 import하기 전에 기존 대상을 확정하고 읽기 전용 URI로 엽니다. DB·WAL과 실제 생성할 롤백·작업 파일 수를 기준으로 데이터·설정·롤백이 위치한 각 파일시스템의 여유 공간을 계산하고 부족하면 변경 전에 중단합니다.
  2. 현재 키와 `key_hash_snapshot`을 원시 SQL로 검사합니다. Docker는 실제 Compose 해석 키와 선택한 `.env`의 지문을 비교하고, 평문 모드이거나 지문이 다르면 중단합니다.
  3. 운영 절차로 앱 종료를 확인한 뒤 새 기동을 막는 유지보수 잠금과 데이터 디렉터리 기준 포터블 뮤텍스를 획득합니다. 잠금·뮤텍스 또는 SQLite 독점 접근 확인이 실패하면 작업을 거부합니다.
  4. 모든 연결을 닫을 수 있는 상태에서 `PRAGMA wal_checkpoint(TRUNCATE)`를 성공시킨 뒤 DB, `-wal`, `-shm`을 하나의 롤백 단위로 취급합니다. 체크포인트나 잔존 파일 격리에 실패하면 교체를 시작하지 않습니다.
  5. 기존 SQLite backup API로 커밋된 WAL 내용을 포함한 롤백 백업과 작업용 DB를 만들고 운영 DB는 직접 부분 수정하지 않습니다.
  6. 작업 ID, 단계, 원본·작업 파일 해시, 축약 키 지문, 암호화 모드와 롤백 자료 위치를 담은 상태 파일과 매니페스트를 먼저 기록합니다. 파일을 닫고 `fsync`하며 지원하는 운영체제에서는 상위 디렉터리까지 동기화합니다.
  7. 원시 SQL과 구키 Fernet으로 정상 암호문, NULL과 복호화 불가 값을 분류합니다. 복호화 불가 값은 기본적으로 손상 가능성이 있다고 보고 작업을 중단하며, Fernet 토큰 형식이 아닌 레거시 평문 후보만 건수와 레코드 식별자를 보고한 뒤 명시적 `--allow-legacy-plaintext` 옵션이 있을 때 변환합니다. 키 원문과 개인정보 값은 보고하지 않고, Fernet 형식이지만 복호화에 실패한 값은 옵션과 관계없이 중단합니다.
  8. 작업 DB의 `key_hash_snapshot`을 갱신하고 모든 사용자의 `token_version`을 증가시켜 구키 JWT가 롤백 후 다시 유효해지지 않게 합니다.
  9. 대상 행 수, 신키 전체 복호화, 구키 복호화 실패, `PRAGMA quick_check`, `PRAGMA foreign_key_check`와 필수 스키마를 검증합니다.
  10. 검증된 같은 디렉터리의 임시 파일을 `os.replace`로 개별 교체하고 기존 WAL·SHM을 롤백 세트로 격리합니다. DB와 설정 교체 전후마다 상태를 기록·동기화하며 `.env`의 다른 값·주석·줄바꿈과 파일 권한·소유자를 보존합니다.
  11. 신키 기준 백업을 생성·검증하고 자동복구 후보의 키 호환성을 확인합니다.
  12. 중단 후에는 명시적 `--resume` 또는 `--rollback`과 상태 파일 해시로 원본 복구 또는 신키 완료를 수행하고 중복 변환을 방지합니다. 롤백 DB에서도 모든 `token_version`을 증가시킵니다.
  13. 로테이션 전 DB·구키·설정 백업과 연결 정보는 로테이션 이전 자동 백업이 보존 정책에 따라 모두 제거되고 구키 복구 리허설이 끝날 때까지 보존하며 도구가 이를 자동 삭제하지 않습니다.
- **운영 절차**:
  - 포터블은 트레이에서 앱을 종료한 뒤 `SHIM_Portable.exe maintenance ...`를 실행하고 앱을 다시 시작합니다.
  - Docker는 중지 전에 Compose 최종 설정, 데이터 경로, 사용할 이미지 태그·이미지 ID와 로컬 존재 여부를 확인한 뒤 `docker compose down → 동일 이미지로 유지보수 명령 → docker compose up -d` 순서로 수행합니다.
  - 운영 가이드에서 데이터 삭제 위험이 있는 `docker compose down -v`와 `docker compose rm -v`를 금지합니다.
  - Docker 유지보수 컨테이너는 배포 루트와 실제 데이터 경로만 읽기·쓰기 마운트하고 가능하면 호스트 UID/GID로 실행해 파일 소유권을 보존합니다.
  - Linux 배포판 이름을 일괄 지원한다고 표현하지 않고 Docker Engine, Compose v2, 지원 CPU 아키텍처, bind mount 쓰기 권한을 지원 조건으로 문서화합니다. rootless Docker와 SELinux 호스트는 UID/GID 및 `:Z` 같은 호스트별 마운트 옵션을 별도로 안내합니다.
  - CLI와 bind mount를 제공하지 않는 NAS 전용 UI는 일반 Linux Docker 절차의 지원 범위로 간주하지 않고 별도 검증 후 안내합니다.
  - 유지보수 도구는 앱이나 Docker를 직접 종료·시작하거나 프로세스를 강제 종료하지 않습니다.

  - 단일 구현을 위한 인터페이스·팩토리·플러그인 계층은 만들지 않습니다.

  - 무중단 라이브 로테이션과 런타임 다중 키 키링을 도입하지 않습니다.
  - 초기 구현에서 별도 유지보수 OCI 이미지와 별도 PyInstaller EXE를 만들지 않습니다.

  - 프로세스 강제 종료, Docker·앱 수명주기 제어, 범용 스키마 자동 변경, DB 최적화 버튼, 사용자 일괄 관리와 자체 스케줄러를 포함하지 않습니다.
- **MVP 완료 기준**:
  - 잘못된 구키, 손상 암호문, 평문 모드, NULL·평문 레거시 값, 디스크 공간 부족과 파일 교체 각 단계의 강제 종료를 검증합니다.
  - 복호화 불가 값을 기본 거부하고, 명시적으로 허용한 비-Fernet 레거시 평문 후보만 변환하며 Fernet 형식의 손상 값은 계속 거부하는지 확인합니다.
  - 운영 DB 복제본의 모든 대상 행을 신키로 복호화할 수 있고 신 암호문은 구키로 복호화할 수 없음을 확인합니다.
  - 모델 메타데이터에서 발견한 모든 `EncryptedString` 컬럼을 정확히 한 번 처리하고, 전체 대상 컬럼에서 구키로 복호화 가능한 값이 남지 않음을 확인합니다.
  - 과거 자동 백업은 함께 보존한 구키로 계속 검증할 수 있음을 확인합니다.
  - `key_hash_snapshot`, JWT 재로그인, 성공·롤백 후 전체 `token_version` 증가, 기존 세션 비활성 유지와 SQLite 무결성을 확인합니다.
  - `verify`와 `verify-backup`이 DB·키·암호문·백업을 변경하지 않고 민감정보를 출력하지 않음을 확인합니다.
  - DB와 설정 교체 사이에 중단해도 재실행으로 원본 복구 또는 신키 완료가 가능함을 확인합니다.
  - WAL 체크포인트 전후, WAL·SHM 격리, 상태 파일·DB·설정 교체와 신키 백업 생성 단계마다 강제 종료해 `--resume`과 `--rollback`을 검증합니다.
  - 자동복구가 신키와 호환되는 백업만 선택하고 구키 백업과 `key_hash_snapshot`이 없는 레거시 백업은 구조적으로 정상이더라도 제외하는지 확인합니다.
  - 실제 Compose 해석 키와 선택한 `.env`의 지문 불일치에서 변경 전에 중단하고, 설정 교체 뒤 다음 Compose 해석 키와 DB 지문이 일치해야 재기동을 허용하는지 확인합니다.
  - `.env`와 `secret.key`의 기존 권한·소유권·비관련 설정이 보존됨을 확인합니다.
  - 읽기 전용 진단과 빠른 오류 검사는 smoke, 단계별 강제 종료·재개·롤백과 배포 리허설은 release 검사에 등록합니다. `CI-001` 착수 전에도 로컬에서 같은 검사를 수행합니다.
  - 포터블과 Docker에서 종료·로테이션·재기동·구키 백업 검증·롤백을 실제로 리허설하고 운영 문서를 갱신합니다.
  - Linux Docker는 특정 배포판 수를 보장하는 대신 지원 조건을 충족하는 `amd64` 환경과 실제 제공하는 경우 `arm64` 환경에서 동일 이미지 명령을 검증합니다.

## ⏳ 3. 장기 보류 및 요구 발생 시 재검토 (P3)

### [AUTH-002] 로그인 남용 방어

- **착수 조건**: 신뢰할 수 없는 내부 사용자가 로그인 화면에 접근하거나, 반복 실패 기록·보안 감사 요구가 확인됐을 때 착수합니다.
- **기본 방향**:
  - 관리자 특례와 장시간 강제 잠금보다 짧은 지연 또는 IP·계정 조합별 제한을 우선 검토합니다.
  - 프록시 사용 여부와 신뢰할 수 있는 클라이언트 IP 판정 방식을 먼저 확정합니다.
  - 단일 프로세스 요구가 유지되는 동안은 표준 라이브러리 기반의 작고 동시성 안전한 구현을 우선하며 `slowapi`를 기본 전제로 두지 않습니다.
  - 영구 계정 잠금이나 DB 컬럼 추가는 고객 보안 정책이 명시적으로 요구할 때만 검토합니다.
- **완료 기준**: 정상 로그인, 실패 누적·해제, 동시 요청, 프록시 환경, 재시작 정책과 관리자 계정 서비스 거부 가능성을 검증합니다.

## 🚫 4. 현재 계획에서 채택하지 않는 범위

다음 항목은 현재 SHIM의 규모와 운영 구조에 비해 효과가 불명확하거나 위험이 더 크므로 즉시 개선과제로 채택하지 않습니다.

- 실제 고객 요구가 없는 OAuth, Redmine, 웹소켓, 외부 API와 프록시 구축
- `slowapi`, `structlog` 등 현재 요구를 표준 라이브러리로 충족할 수 있는 신규 런타임 의존성
- 관리자 3회 실패·30분 잠금처럼 근거 없이 고정된 계정 잠금 정책
- 공개 `/health` 응답의 디스크·백업·내부 오류 세부 정보
- 중앙 로그 수집기 없는 환경의 전면 JSON 구조화 로깅
- 서비스 운영 중 배치 커밋으로 수행하는 무중단 PII 키 로테이션
- 실패를 `|| true`로 무시하는 감사·정적 분석 단계
- 기준선 정리 없이 도입하는 `mypy --strict`와 전면 lint 수정
- 여러 보안·운영 변경을 짧은 고정 일정으로 묶어 즉시 프로덕션 준비 완료라고 판단하는 방식

## 📝 5. 구현 시 문서 동기화 범위

아직 구현·검증되지 않은 명령과 설정을 현재 사용 가능한 절차처럼 안내하지 않습니다. 각 작업 ID의 코드, 테스트와 아래 문서 변경이 함께 완료된 경우에만 운영 가능한 개선으로 판단합니다.

- **공통 역할 분리**:
  - `README.md`는 지원 환경, 핵심 보안 주의사항과 공식 진입 문서를 안내합니다.
  - `docs/1-1_초심자_구동_가이드.md`는 최초 실행과 최소 상태 확인까지만 간단히 안내하고, 데이터 교체와 롤백 상세 절차는 싣지 않습니다.
  - `docs/1-2_백업_복구_유지보수_가이드.md`는 서비스 중지, 사전 백업, 유지보수 실행, 검증, 재기동과 롤백을 포함한 운영 절차의 기준 문서로 사용합니다.
  - `portable/README_PORTABLE.md`는 Windows 최종 사용자 절차, `portable/README.md`는 빌드·패키징과 개발자 검증 범위를 담당합니다.
  - `openwiki/architecture.md`, `openwiki/operations.md`, `openwiki/testing.md`에는 구현 구조, 운영 제약과 재현 가능한 검증 방법을 반영합니다.
  - 환경 변수가 추가되거나 의미가 바뀌면 `infra/docker/.env.example`과 관련 Compose 설명을 함께 갱신합니다.
- **과제별 필수 갱신**:
  - `OPS-004`: 초심자·유지보수·포터블 가이드와 OpenWiki 운영 문서에 포터블 로그 경로, 순환 범위와 장애 확인 순서를 반영합니다.
  - `DB-001`: 실제 착수 시에만 지원 기준 DB 버전, `pre_migration` 백업, 재실행·롤백과 검증 절차를 유지보수 가이드와 OpenWiki 운영·테스트에 반영합니다.
  - `SEC-004`: README와 초심자 가이드에는 수동 키 변경 금지와 유지보수 명령 진입점만 안내하고, 상세 중지·키 생성·로테이션·검증·롤백 절차는 유지보수 가이드에 둡니다. Docker와 포터블 명령, 경로, 권한 차이는 각 배포 가이드에 별도로 설명합니다.
  - `AUTH-002`와 `reset-admin-password` 후속 명령을 구현하면 잠금·해제·비상 복구와 세션 무효화 절차를 README, 유지보수 가이드와 보안 설계에 함께 반영합니다.
- **현재 안내와의 전환 규칙**:
  - 암호화 모드 안에서 수행하는 `rotate-key`, 랜덤 키 파일만 생성하는 `generate-key`, 평문 설치본을 암호화 모드로 바꾸는 조건부 `enable-encryption`을 서로 다른 작업으로 설명합니다.
  - Linux Docker는 배포판 이름보다 Docker·Compose·권한·아키텍처 지원 조건을 기준으로 안내합니다.
- **완료 문서 처리**:
  - 구현 후의 현재 구조만 `docs/4-1_SHIM_프로젝트_설계서.md`에 반영하고 변경 이력을 섞지 않습니다.
  - 완료 증적과 검증 결과는 `docs/2-1_운영_릴리즈_통합_산출물.md`로 이관한 뒤 해당 백로그를 이 문서에서 삭제합니다.
  - 새 문서를 추가하지 않는 한 `docs/0_문서_인덱스.md`는 변경하지 않습니다.

## 🗺️ 6. 조건부 재평가 순서

1. `OPS-004` 포터블 순환 파일 로그
2. `DB-001`은 보존할 기존 DB나 실제 스키마 변경 요구가 생길 때 착수
3. `SEC-004`는 실제 키 교체 요구가 발생할 때 포터블·Docker 복제 데이터에서 MVP를 먼저 검증
4. `CI-001`은 협업·PR 게이트·반복 배포·의존성 변경 등 착수 조건이 발생할 때 도입
5. `AUTH-002`는 명시적 보안·접근 환경 요구가 발생할 때 재평가

각 과제는 독립 구현·검증합니다. CI 도입 전에는 기존 로컬 `smoke`·`release`와 표적 테스트를 검증 기준으로 유지하며, DB 마이그레이션과 데이터 교체 도구는 각각의 착수 조건이 충족된 별도 작업으로 진행합니다.

## 🧭 7. 작업 인수인계 규칙

1. 작업 전에 `openwiki/quickstart.md`와 해당 영역 문서를 읽습니다.
2. 한 번에 하나의 작업 ID만 선택하고 기존 증적의 ID를 재사용하지 않습니다.
3. `git status --short`와 대상 diff를 확인하고 사용자 미커밋 변경을 보존합니다.
4. 표적 테스트를 먼저 추가하고 신규 테스트를 `tools/scripts/run_tests.py`에 등록합니다.
5. 공통 검증 명령과 배포 형태별 확인 절차는 `openwiki/testing.md` 및 해당 운영 가이드를 따릅니다.
6. 구현 또는 검증이 남으면 완료 처리하지 않고 남은 조건과 차단 사유를 유지합니다.
7. 완료 후 이 문서에서 해당 항목을 삭제하고 증적은 `docs/2-1_운영_릴리즈_통합_산출물.md`, 변경된 현재 설계는 `docs/4-1_SHIM_프로젝트_설계서.md`에 반영합니다.
8. 운영·보안·포터블 동작이 바뀌면 README와 해당 운영 가이드도 같은 작업 ID 안에서 갱신합니다.
