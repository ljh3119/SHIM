# 향후 개선계획 (Product Roadmap)

이 문서는 아직 완료되지 않은 백로그만 관리합니다. 완료된 변경과 검증 증적은 `docs/2-1_운영_릴리즈_통합_산출물.md`, 구현 후의 현재 구조는 `docs/4-1_SHIM_프로젝트_설계서.md`에서 관리합니다.

SHIM은 폐쇄망에서 로컬 Windows, Docker, 포터블 실행을 지원하는 단일 FastAPI·SQLite 애플리케이션입니다. 새 서버·서비스·런타임 의존성은 실제 운영 요구가 확인된 경우에만 추가하고, 기존 코드와 Python 표준 라이브러리로 해결 가능한 범위를 우선합니다.

---

## 1. 검증 기준과 현재 상태

- **기준 일자**: 2026-08-17
- **기준 버전**: `1.9.8`
- **기준 상태**: v1.9.8 구현·검증이 완료됐지만 아직 커밋·태그·push되지 않은 릴리스 후보 작업 트리를 기준으로 합니다.
- `AUTH-003`, `OPS-004`, `SEC-005`는 구현과 표적·smoke·release 검사를 마쳤습니다. `OPS-004`는 실제 master·worker·트레이 종료 event, worker 실패 코드 보존, 트레이 등록 실패 시 worker·DB 미생성, lifespan·Uvicorn 종료와 WAL/SHM 정리까지 회귀 검사합니다. 같은 소스의 Docker 두 태그와 Windows x64 포터블 ZIP도 실기동 검증했으며 상세 증적은 릴리스 통합 산출물에 기록했습니다.
- `DEP-001`의 코드·감사·산출물 검증은 끝났지만 GitHub 게시 후 Dependabot 경고 종료 확인이 남아 있으므로 아래 게시 확인 대기 과제로 유지합니다.
- 자동복구는 현재 애플리케이션이 요구하는 스키마 완료 상태와 호환되는 백업만 허용합니다. 구버전 DB 마이그레이션은 자동복구와 결합하지 않습니다.
- 수정 버전이 없는 `ecdsa 0.19.2 / PYSEC-2026-1325`는 SHIM이 HS256만 허용하고 ECDSA·ECDH 경로를 사용하지 않는다는 근거로 해당 ID만 제한적으로 수용합니다.
- 저장소가 직접 관리하는 GitHub Actions 워크플로와 `main` 브랜치 보호는 아직 없습니다. 사용자 결정에 따라 `CI-001`은 다른 남은 과제를 검토한 뒤 가장 마지막에 처리합니다.

### 공통 원칙

- 기존 테스트·작업 로그·릴리스 증적에서 사용한 작업 ID를 다른 의미로 재사용하지 않습니다.
- 한 번에 하나의 작업 ID만 구현하고 표적 테스트를 먼저 추가합니다.
- 신규 테스트는 `tools/scripts/run_tests.py`의 smoke 또는 release 목록에 등록합니다.
- 운영 DB·키·설정 파일을 바꾸는 작업은 서비스 중지, 검증된 사전 백업, 실패 복구와 배포 형태별 리허설을 완료하기 전 운영 가능으로 판단하지 않습니다.
- 공개 HTTP 응답에는 경로, SQL, 예외 원문, 키, 암호문, 개인정보와 백업 세부 정보를 노출하지 않습니다.
- 구현이나 Docker·포터블 실환경 검증이 남으면 해당 과제를 완료 처리하지 않습니다.

## 2. 게시 확인 대기

### [DEP-001] cryptography 보안 업데이트 게시 확인

- **완료된 범위**: `cryptography 50.0.0` 고정, Windows 64비트 Python 3.12의 Fernet·HS256, 전체 smoke·release, `pip check`, `pip-audit==2.10.1`, Docker와 포터블 실기동 검증을 완료했습니다.
- **남은 작업**:
  - v1.9.8 변경을 커밋·태그·push한 뒤 `origin/main`의 `requirements.txt`와 배포 산출물이 `cryptography 50.0.0`을 사용하는지 확인합니다.
  - GitHub Dependabot에서 기존 `cryptography` 경고가 자동 종료됐는지 확인합니다. 자동 종료되지 않으면 경고가 참조하는 manifest와 브랜치, 실제 감사 결과를 대조하며 근거 없이 수동 종료하지 않습니다.
- **완료 기준**: 게시된 커밋·태그 식별값과 Dependabot 경고 종료 상태를 릴리스 통합 산출물에 기록한 뒤 이 항목을 삭제합니다.

## 3. 조건부 개선 과제

현재 즉시 착수할 필수 과제는 없습니다. 아래 과제는 적힌 조건이 실제로 확인될 때만 착수합니다.

### [DB-001] SQLite 스키마 마이그레이션 안전성 보강

- **현재 판단**: 저장소의 로컬 DB에는 데이터가 있지만 운영 데이터인지 개발 데이터인지 확인할 수 없습니다. “실제 사용자가 없다”는 전제를 코드나 문서에서 확정하지 않습니다.
- **착수 조건**:
  - 보존해야 할 배포 DB가 확인되거나,
  - 배포된 DB의 컬럼·인덱스·외래키를 변경하는 다음 요구가 생길 때 실제 스키마 변경보다 먼저 착수합니다.
- **필요 시 구현 범위**:
  - 배포 담당자가 지원 기준 DB 버전과 보존 대상 설치본을 먼저 명시합니다.
  - 기존 `schema_versions`, 초기화 잠금, SQLite backup API와 `quick_check`를 재사용합니다.
  - `Base.metadata.create_all()`이나 버전별 마이그레이션보다 앞서 일반 순환 백업과 분리된 `pre_migration` 백업을 만들고, 검증 성공 시에만 초기화를 계속합니다.
  - 실제 변경에 필요한 버전별·멱등 마이그레이션과 지원 대상 DB 복제본 테스트만 추가합니다.
- **제외 범위**:
  - 배포 여부 확인 없이 모든 과거 개발 DB를 소급 지원하지 않습니다.
  - 구체적인 스키마 변경 전에 범용 마이그레이션 프레임워크를 만들지 않습니다.
  - 현재 자동복구에 구버전 DB 마이그레이션을 결합하지 않습니다.
- **완료 기준**:
  - 지원 대상 DB 복제본에서 성공·실패·재실행·중단 복구, 행 수, `quick_check`, 외래키, 인덱스와 `schema_versions` 정합성을 검증합니다.
  - 실패 시 검증된 `pre_migration` 백업으로 운영자가 복구할 수 있고 원본과 실패 증적이 보존되는지 확인합니다.

### [SEC-004] 오프라인 암호화 키 로테이션

- **착수 조건**:
  - 암호화 모드의 실제 운영 배포에서 키 유출 대응, 정기 교체 정책 또는 고객 보안 요구가 확인되고,
  - 포터블·Docker 운영 복제본으로 중단·복구 리허설을 수행할 수 있을 때 착수합니다.
- **단계별 범위**:
  1. 읽기 전용 `verify`·`verify-backup`으로 DB 무결성, 지원 스키마, 현재 키 지문과 대상 암호문을 변경 없이 검사합니다.
  2. 서버를 완전히 중지한 상태에서 롤백 백업과 작업용 DB를 만들고 작업용 DB만 새 키로 재암호화합니다.
  3. 새 키 전체 복호화, 이전 키 복호화 실패, 행 수, `quick_check`, 외래키와 `key_hash_snapshot`을 검증한 뒤 DB와 키 설정을 각각 원자적으로 교체합니다. 두 대상을 하나의 원자 연산으로 오인하지 않습니다.
  4. 전체 `token_version`을 증가시키고 새 키 호환 백업을 생성·검증한 뒤 재기동합니다.
  5. DB와 설정 교체 사이의 강제 종료를 포함해 명시적 재개·롤백을 리허설합니다.
- **필수 안전 원칙**:
  - 키 원문을 명령행, 로그와 보고서에 출력하지 않습니다.
  - 평문 설치본은 `rotate-key`로 변환하지 않고 별도 요구의 `enable-encryption` 과제로 다룹니다.
  - 운영 DB를 행 단위로 직접 부분 변경하지 않고 작업 복제본을 검증한 뒤 교체합니다.
  - 포터블 키 파일과 Docker 외부 환경변수의 교체 절차를 분리하고, 작은 상태 파일로 중간 종료 시 재개 또는 이전 DB·키 세트 롤백을 지원합니다.
  - 이전 키 DB·키·설정 세트는 과거 백업의 보존 기간과 복구 리허설 완료 전까지 보존합니다.
  - 별도 GUI, 별도 유지보수 이미지와 무중단 다중 키 키링은 만들지 않습니다.
- **완료 기준**:
  - 잘못된 이전 키, 손상 암호문, 디스크 부족, WAL·SHM, 파일 교체 단계 중단, 재개·롤백과 권한 보존을 검증합니다.
  - 포터블과 Docker에서 중지→검증→로테이션→재기동→이전 키 백업 검증→롤백을 실제 리허설합니다.
  - 구현되지 않은 `rotate-key`, `verify-backup`, `enable-encryption` 명령을 현재 사용 가능한 절차처럼 문서화하지 않습니다.

### [AUTH-002] 로그인 남용 제한

- **착수 조건**: 반복 로그인 실패 기록, 신뢰할 수 없는 내부 접근 또는 고객 보안 감사 요구가 확인될 때 착수합니다.
- **구현 전 결정 사항**:
  - 직접 접속인지 역방향 프록시 뒤인지 확인하고 신뢰 가능한 클라이언트 IP 판정 방식을 먼저 확정합니다.
  - 재시작 시 제한 상태 초기화를 허용할지, 단일 프로세스 유지 여부와 허용 실패율·해제 시간을 운영 정책으로 정합니다.
- **기본 방향**:
  - 장시간 계정 잠금보다 짧은 지연 또는 IP·계정 조합별 제한을 우선합니다.
  - 단일 프로세스에서는 표준 라이브러리 기반의 작고 동시성 안전한 메모리 제한기를 우선하고 `slowapi`를 기본 전제로 두지 않습니다.
  - 관리자 특례, 영구 잠금과 DB 컬럼 추가는 명시적 고객 정책이 있을 때만 검토합니다.
- **완료 기준**:
  - 정상 로그인, 실패 누적·해제, 동시 요청, 프록시 환경, 재시작과 관리자 계정 서비스 거부 가능성을 검증합니다.
  - 제한 응답은 내부 계정 존재 여부를 추가로 노출하지 않고 정상 사용자를 과도하게 차단하지 않습니다.

## 4. 최종 후순위 과제

### [CI-001] 최소 지속적 검증 및 의존성 감사

- **처리 순서**: 사용자 결정에 따라 남은 과제 중 가장 마지막에 검토·구현합니다. 앞의 조건부 과제가 아직 미착수여도 CI 착수 시점은 별도로 승인받습니다.
- **현재 판단**: 저장소가 직접 관리하는 Actions 워크플로와 브랜치 보호가 없고 로컬 pre-push 훅이 전체 smoke·의존성 감사를 실행하지 않습니다. Dependabot 보안 업데이트와 GitHub 관리형 Dependency Graph는 이미 활성화되어 있습니다.
- **최소 워크플로**:
  - Python 3.12에서 `requirements-dev.txt`를 설치합니다.
  - 검증된 고정 버전의 `pip-audit`를 별도 설치하고 Python 전체 컴파일, 버전 정합성, smoke와 `pip-audit -r requirements.txt`를 구분된 단계로 실행합니다.
  - Node 의존성 변경 시 `npm ci`와 `npm audit`을 실행합니다.
  - GitHub Actions 권한은 `contents: read`를 기본으로 하고 외부 Action과 감사 도구 버전을 검증된 값으로 고정합니다.
  - 실패를 `|| true`로 무시하지 않습니다. 이미 분석·수용한 `PYSEC-2026-1325`만 식별자, 영향 범위와 만료 조건을 기록해 제한적으로 예외 처리합니다.
- **저장소 설정**:
  - 워크플로가 안정화되고 실제 PR 기반 운영을 사용할 때 `main` 보호와 필수 상태 검사를 연결합니다.
  - secret scanning과 push protection은 저장소·계정에서 제공되는 범위를 확인한 뒤 활성화를 검토합니다.
- **제외 범위**:
  - 모든 push에 release·메모리 1,000회·Docker·포터블 빌드를 강제하지 않습니다. release 또는 배포 후보에서 별도로 수행합니다.
  - 기준선 없는 `mypy --strict`, 전면 lint 수정과 자동 배포를 추가하지 않습니다.
- **완료 기준**:
  - 정상 브랜치에서 필수 단계가 통과하고 의도적으로 실패시킨 테스트·버전 불일치·신규 미수용 감사 경고가 워크플로를 실패시킵니다.
  - 로컬 훅을 우회해도 원격 검사 결과가 남고, PR 보호를 사용한다면 실패 상태에서 병합이 차단됩니다.
  - 감사 결과 또는 승인된 예외를 릴리스 증적에 기록합니다.

## 5. 현재 채택하지 않는 범위

- 실제 고객 요구가 없는 OAuth, Redmine, 웹소켓, 외부 API와 프록시 구축
- `slowapi`, `structlog`처럼 현재 요구를 표준 라이브러리로 충족할 수 있는 신규 런타임 의존성
- 관리자 3회 실패·30분 잠금처럼 근거 없이 고정된 계정 잠금 정책
- 공개 `/health` 응답의 디스크·백업·내부 오류 세부 정보
- 중앙 로그 수집기 없는 환경의 전면 JSON 구조화 로깅
- 서비스 운영 중 수행하는 무중단 PII 키 로테이션과 다중 키 키링
- 실패를 `|| true`로 무시하는 감사·정적 분석 단계
- 기준선 없이 도입하는 `mypy --strict`, 전면 lint 수정과 자동 배포
- 구체적인 스키마 변경 전에 만드는 범용 마이그레이션 프레임워크

## 6. 구현 순서와 완료 처리

1. `DEP-001` — v1.9.8 게시 직후 Dependabot 종료 상태 확인
2. `DB-001` — 실제 배포 DB 또는 다음 스키마 변경 요구가 확인될 때
3. `SEC-004` — 암호화 키 교체 요구와 배포별 리허설 환경이 확보될 때
4. `AUTH-002` — 접근 환경과 제한 정책이 확정될 때
5. `CI-001` — 사용자 별도 승인 후 가장 마지막에 처리

조건부 과제는 앞 번호가 끝났다는 이유만으로 자동 착수하지 않습니다. 각 작업은 독립적으로 구현·검증하고, 일부 구현이나 실환경 검증이 남으면 완료 처리하지 않습니다.

완료 시 다음 원칙을 적용합니다.

1. 구현 후 현재 구조는 `docs/4-1_SHIM_프로젝트_설계서.md`와 관련 OpenWiki에 반영합니다.
2. 검사 결과와 산출물 식별값은 `docs/2-1_운영_릴리즈_통합_산출물.md`로 이관합니다.
3. 해당 작업 ID를 이 문서에서 삭제합니다.
4. 새 문서를 추가하지 않았다면 `docs/0_문서_인덱스.md`는 변경하지 않습니다.

## 7. 작업 인수인계 규칙

1. 작업 전에 `openwiki/quickstart.md`와 해당 영역 문서를 읽습니다.
2. `git status --short`와 대상 diff를 확인하고 사용자 미커밋 변경을 보존합니다.
3. 재현 테스트를 먼저 추가하고 smoke 또는 release 목록에 등록합니다.
4. 표적 테스트, smoke, 필요한 release와 Docker·포터블 실환경 검증을 순서대로 수행합니다.
5. 운영·보안·포터블 동작이 바뀌면 코드와 같은 작업 ID에서 관련 문서를 갱신합니다.
